Актуальная рабочая версия: **v2.26**.

Этот файл предназначен для продолжения разработки курса в новом чате. Он не включается в навигацию GitHub Pages.

## 1. Цель и аудитория

Дисциплина: **«Системы обнаружения и предотвращения вторжений (IDPS)»**.

Аудитория: студенты 4 курса специальности **«Системы информационной безопасности»**.

Курс является университетской инженерной дисциплиной об IDS/IPS как классе систем защиты. Он не строится как обучение профессии SOC Analyst, Security Engineer или Architect. Профессиональные роли могут использоваться только как отдельные примеры применения.

Основная цель:

> Сформировать целостное инженерное представление о системах обнаружения и предотвращения вторжений: источниках данных, принципах наблюдения, способах анализа, методах обнаружения, размещении, ограничениях видимости, предотвращении, оценке эффективности и эксплуатации.

Suricata, Zeek, Wazuh и другие продукты являются реализациями изучаемых принципов, а не предметом курса сами по себе.

## 2. Замороженная дидактическая структура

1. Что такое IDS/IPS и зачем они нужны.
2. Какие существуют виды IDS/IPS.
3. Из чего состоит IDS/IPS и как она работает.
4. Где и как размещают IDS/IPS.
5. Как IDS/IPS обнаруживает подозрительную активность.
6. Что такое правила и как они устроены.
7. Почему IDS/IPS ошибается и чего она не видит.
8. Как проверить и обосновать эффективность IDS/IPS.

Эту последовательность не менять без реальной технической причины.

## 4. Лабораторная среда

Основной стенд:

- `idps-client` — Ubuntu Desktop 24.04.x — `10.13.37.10/24`;
- `idps-server` — Ubuntu Server 24.04.x — `10.13.37.20/24`;
- VirtualBox;
- Adapter 1 = NAT;
- Adapter 2 = Internal Network `IDPS-LAB`;
- учебная сеть `10.13.37.0/24` не имеет второго default gateway.

Студент самостоятельно разворачивает обе VM и использует `env-setup` для установки зависимостей и проверки готовности.

`CLIENT ENVIRONMENT READY` / `SERVER ENVIRONMENT READY` подтверждают readiness среды, но **не** runtime-работоспособность конкретной лабораторной.

## 5. Правила проектирования лабораторных

1. Лабораторная непосредственно закрепляет уже изученную теорию.
2. Не использовать как обязательные понятия темы, которые появятся только в следующих главах.
3. Один эксперимент должен изолировать понятную переменную.
4. Отсутствие alert/записи не является самостоятельным доказательством отсутствия исходного события.
5. Если вывод требует ground truth, использовать независимый источник проверки.
6. `pre-flight` ≠ `runtime verification`.
7. Скрипты проходят static QA, но работа получает `RUNTIME VERIFIED` только после end-to-end прогона на эталонных VM.
8. Не скрывать предположения об интерфейсе, маршруте, шифровании, parser state или доступной telemetry.
9. Студент должен уметь объяснить, **что именно доказал эксперимент и чего он не доказал**.
10. Готовые правила допустимы до Главы 6; самостоятельное написание правил до изучения их устройства не требуется.

## 6. Критические логические ошибки, которые нельзя возвращать

- `Firewall = только L3/L4`.
- `IDS = passive`, `IPS = inline`.
- `ALERT = INCIDENT = COMPROMISE`.
- отсутствие alert = отсутствие traffic.
- `Network / Host / Wireless / Behavioral` как четыре равноправные оси.
- `Behavioral = Anomaly`.
- universal pipeline `packet → decode → stream → parser → detection`.
- detection якобы начинается только после application parser.
- HIDS автоматически «видит всё на хосте».
- один application log является ground truth для любой L3/L4 активности.
- `SPAN/TAP` как detection method.
- точка наблюдения объявляется хорошей/плохой без указания конкретного потока.
- parser-derived field автоматически объявляется stateful protocol analysis.
- anomaly автоматически объявляется attack.
- сигнатурное совпадение объявляется доказательством успешной эксплуатации.
- TP/FP/FN считаются без фиксированных evaluation unit/objective/ground truth/population.

## 7. Язык курса

Основной язык — русский.

Английский используется только:

- при первом вводе международного термина, если это полезно для чтения источников;
- для устоявшихся аббревиатур (`IDS`, `IPS`, `NIDS`, `WAF`, `NBA` и т.п.);
- для буквального синтаксиса продукта (`http.uri`, `flow`, `sid`, `detection_filter`).

Не чередовать без необходимости `detection / обнаружение / detector / alert / evidence` в русскоязычном тексте.

## 8. Визуальный стандарт

Схема публикуется только если она помогает увидеть отношение быстрее текста.

Для каждой схемы должны быть понятны:

1. что она объясняет;
2. что означает каждая стрелка;
3. какой вывод из неё следует.

Не использовать большие рамки с текстом как псевдосхемы.

Семантика стрелок должна быть явной, если на одной схеме есть разные типы связей: основной поток, копия, управляющее воздействие и т.д.

## 9. Источники

Приоритет:

1. стандарт / RFC / официальная документация;
2. первичный или near-primary incident material;
3. научная публикация;
4. textbook для педагогического объяснения;
5. course synthesis — явно как наша модель;
6. synthetic lab — явно как учебный сценарий.

NIST SP 800-94 используется как **исторический фундаментальный источник**, а не современная рыночная taxonomy.

## 10. Глава 5 / ЛР №4 — важные решения

Глава 5 разделяет:

- сигнатурный метод;
- `stateful protocol analysis` как классический метод NIST;
- поведенческую логику как учебную инженерную категорию;
- аномалийный метод.

`Behavioral ≠ Anomaly`.

ЛР №4 **не использует разные источники под видом «одних данных»**. Все три режима читают один файл `/var/tmp/idps-lab/lab4-access.jsonl` одинаковой структуры. Меняется только условие анализа:

- известный признак в `uri`;
- детерминированная частота событий;
- отклонение `value_length` от базовой линии.

`detectors.py` — прозрачная synthetic course model, не промышленная IDS. Такое решение принято, чтобы в Главе 5 изолировать различие методов. Реальный синтаксис Suricata начинается в Главе 6 / ЛР №5.

Протокольное состояние не насильно имитируется сомнительным тестом; оно возвращается позже при разборе представления, parser/reassembly и ограничений.

## 11. QA

Перед выпуском релиза:

- проверить `bash -n` всех shell scripts;
- `py_compile` всех Python scripts;
- ZIP integrity всех новых bundles;
- существование всех путей `mkdocs.yml`;
- отсутствие ссылок на несуществующие версии bundle;
- source/evidence register актуализировать;
- не писать `RUNTIME VERIFIED`, если нет реального end-to-end прогона.
