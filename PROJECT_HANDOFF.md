## 1. Цель и аудитория

Дисциплина: **«Системы обнаружения и предотвращения вторжений (IDPS)»**.

Аудитория: студенты 4 курса специальности **«Системы информационной безопасности»**.

Курс является университетской инженерной дисциплиной об IDS/IPS как классе систем защиты. Он не строится как обучение профессии SOC Analyst, Security Engineer или Architect. Профессиональные роли могут использоваться только как отдельные примеры применения.

Основная цель:

> Сформировать целостное инженерное представление о системах обнаружения и предотвращения вторжений: источниках данных, принципах наблюдения, способах анализа, методах обнаружения, размещении, ограничениях видимости, предотвращении, оценке эффективности и эксплуатации.

Suricata, Zeek, Wazuh и другие продукты являются реализациями изучаемых принципов, а не предметом курса сами по себе.

## 2. Замороженная дидактическая структура

## 5. Правила проектирования лабораторных

1. Лабораторная непосредственно закрепляет уже изученную теорию.
2. Не использовать как обязательные понятия темы, которые появятся только в следующих главах.
3. Один эксперимент должен изолировать понятную переменную.
4. Отсутствие оповещения/записи не является самостоятельным доказательством отсутствия исходного события.
5. Если вывод требует независимого подтверждения исходного события, использовать независимый источник проверки.
6. предварительная проверка среды ≠ полный сквозной прогон лабораторной.
7. Скрипты проходят статическую проверку, но работа считается проверенной полным прогоном только после сквозного выполнения на эталонных VM.
8. Не скрывать предположения об интерфейсе, маршруте, шифровании, состоянии разбора протокола или доступной телеметрии.
9. Студент должен уметь объяснить, **что именно доказал эксперимент и чего он не доказал**.
10. Готовые правила допустимы до Главы 6; самостоятельное написание правил до изучения их устройства не требуется.

## 6. Критические логические ошибки, которые нельзя возвращать

- `Firewall = только L3/L4`.
- `IDS = passive`, `IPS = inline`.
- `ALERT = INCIDENT = COMPROMISE`.
- отсутствие оповещения = отсутствие трафика.
- `Network / Host / Wireless / Behavioral` как четыре равноправные оси.
- `Behavioral = Anomaly`.
- универсальный конвейер `packet → decode → stream → parser → detection`.
- обнаружение якобы начинается только после прикладного разбора протокола.
- HIDS автоматически «видит всё на хосте».
- один журнал приложения является универсальным подтверждением любой L3/L4-активности.
- `SPAN/TAP` как метод обнаружения.
- точка наблюдения объявляется хорошей/плохой без указания конкретного потока.
- поле, полученное парсером, автоматически объявляется stateful protocol analysis.
- аномалия автоматически объявляется атакой.
- сигнатурное совпадение объявляется доказательством успешной эксплуатации.
- TP/FP/FN считаются без фиксированных объекта оценки / цели обнаружения / ground truth / выборки оценки.

## 8. Визуальный стандарт

Схема публикуется только если она помогает увидеть отношение быстрее текста.

Для каждой схемы должны быть понятны:

1. что она объясняет;
2. что означает каждая стрелка;
3. какой вывод из неё следует.

Не использовать большие рамки с текстом как псевдосхемы.

Семантика стрелок должна быть явной, если на одной схеме есть разные типы связей: основной поток, копия, управляющее воздействие и т.д.

## 9. Источники

Приоритет:

1. стандарт / RFC / официальная документация;
2. первичный или материал, максимально близкий к первичному источнику инцидента;
3. научная публикация;
4. учебник для педагогического объяснения;
5. синтез курса — явно как наша модель;
6. синтетическая лабораторная — явно как учебный сценарий.

NIST SP 800-94 используется как **исторический фундаментальный источник**, а не современная рыночная классификация.

## 10. Глава 5 / ЛР №4 — важные решения

Глава 5 разделяет:

- сигнатурный метод;
- анализ протокола с учётом состояния (`stateful protocol analysis`) как классический метод NIST;
- поведенческую логику как учебную инженерную категорию;
- аномалийный метод.

Поведенческая логика не тождественна аномалийному методу.

ЛР №4 **не использует разные источники под видом «одних данных»**. Все три режима читают один файл `/var/tmp/idps-lab/lab4-access.jsonl` одинаковой структуры. Меняется только условие анализа:

- известный признак в `uri`;
- детерминированная частота событий;
- отклонение `value_length` от базовой линии.

`detectors.py` — прозрачная синтетическая модель курса, не промышленная IDS. Такое решение принято, чтобы в Главе 5 изолировать различие методов. Реальный синтаксис Suricata начинается в Главе 6 / ЛР №5.

Протокольное состояние не насильно имитируется сомнительным тестом; оно возвращается позже при разборе представления данных, состояния протокола, сборки потока и ограничений.

## 12. Глава 6 / ЛР №5 — важные решения

Глава 6 впервые вводит синтаксис правил Suricata после того, как в Главе 5 студент уже понимает основания обнаружения.

Ключевые границы:

- правило = действие + заголовок + параметры; это учебная декомпозиция синтаксиса, не универсальный внутренний конвейер обработки;
- заголовок задаёт область применения, а `flow`/буфер/`content` уточняют условие;
- `msg`, `sid`, `rev` не объявляются признаками атаки;
- `drop`/`reject` не выдаются за автоматическое блокирование в пассивном IDS-режиме;
- `suricata -T` подтверждает возможность загрузки, но не корректность логики обнаружения;
- `http.uri` вводится как нормализованное представление URI, а детали нормализации/расхождений переносятся в Главу 7.

ЛР №5 использует три этапа: прочитать готовое правило → изменить одно существующее правило → написать собственное правило с двумя прикладными условиями (`GET` + маркер URI). Каждый этап имеет отдельный каталог EVE.

Статус ЛР №5: **требуется проверка полным прогоном** до сквозного выполнения на эталонных Ubuntu Desktop/Server 24.04.x.
