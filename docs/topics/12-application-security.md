# 12. Безопасность приложений

<div class="syllabus-lesson" markdown="1">

<p class="lesson-lead">Безопасность приложения — это корректная работа с вводом, полномочиями, состоянием и доверительными границами. IDS/IPS фиксирует отдельные признаки активности, но сама по себе не исправляет логику приложения.</p>


## 1. Приложение защищают не одними сетевыми правилами

Приложение принимает данные от пользователей, других сервисов и внешних систем. Даже когда транспорт защищён TLS и межсетевой экран допускает только необходимые соединения, внутри приложения остаются собственные **границы доверия**: ввод параметров, выполнение запросов к базе данных, действия от имени пользователя, обращение к другим сервисам.

Поэтому базовая задача AppSec — обеспечить, чтобы каждый вход был правильно интерпретирован, каждое действие выполнялось с необходимыми полномочиями, а важные события можно было расследовать. **Аутентификация** отвечает на вопрос «кто обращается?», **авторизация** — «что именно этому субъекту позволено?». Безопасная аутентификация не заменяет проверку прав на объект.

Рассмотрим учебный API: после входа пользователь обращается к `/orders/42`. Сервер должен проверить не только корректность сессии, но и право конкретного пользователя читать заказ 42. Отсутствие такого контроля способно привести к нарушению авторизации, даже если пароль, MFA и TLS настроены правильно.

## 2. SQL-инъекция: смешение данных с командой

SQL-инъекция возникает, когда данные, которые должно обрабатывать приложение, небезопасно влияют на синтаксис SQL-запроса. Проблема не в том, что строка «выглядит подозрительно», а в **отсутствии корректного разделения параметров и инструкции**. Основная защита — подготовленные запросы с параметризацией, корректные права доступа к БД и проверенная логика доступа.

```python
# Учебный пример безопасного разделения команды и значения
cursor.execute("SELECT status FROM orders WHERE id = ?", (order_id,))
```

Внешняя IDS может наблюдать некоторые признаки в открытом HTTP-запросе, но не обязательно знает, как приложение сформировало SQL. Даже совпадение сигнатуры возможной инъекции не доказывает успешного выполнения произвольной команды в БД. Для такого вывода нужны журналы приложения, БД и проверка фактического результата.

## 3. XSS: данные становятся кодом в браузере

При межсайтовом выполнении сценариев (XSS) небезопасное включение контролируемых данных в HTML/JavaScript может привести к исполнению кода в контексте сайта у пользователя. Основная граница проходит между **данными** и **исполняемым содержимым браузера**.

Подходящая защита зависит от контекста вывода: кодирование данных для HTML, атрибутов, JavaScript и URL различается. Для динамического HTML используют безопасные API работы с DOM. Content Security Policy (CSP) может уменьшать некоторые последствия, но **не заменяет** корректную обработку данных и безопасные шаблоны.

В контексте IDS важно различать попытку включить опасную строку в запрос и подтверждение исполнения в браузере. Сетевой alert обычно свидетельствует только о выполнении условий детектора на доступных данных.

## 4. CSRF: корректная сессия, нежелательная операция

Межсайтовая подделка запроса (CSRF) эксплуатирует ситуацию, когда браузер автоматически прикладывает полномочия пользователя к запросу, инициированному из недоверенного контекста. Поэтому аутентификация пользователя сама по себе не гарантирует, что он намеренно вызвал действие.

Защита включает корректную архитектуру состояния и запросов, CSRF-токены там, где они нужны, настройки SameSite для cookie и проверку происхождения запроса по применимости. Важно не давать универсального совета «всё исправляет один заголовок»: способ защиты зависит от механизма сессий и протокола приложения.

## 5. Управление сессией и полномочиями

Вход с паролем и MFA должен сопровождаться безопасной выдачей и проверкой сессионных данных. Cookie с `Secure`, `HttpOnly` и обоснованным `SameSite`, срок жизни, отзыв сессии, защита от фиксации сессии — это разные меры. Для API может применяться токеновый доступ; наличие и криптографическая корректность токена не заменяют **проверку прав** на запрошенный объект.

Принцип минимально необходимых полномочий снижает последствия ошибки, но не исправляет уязвимую бизнес-логику. Поэтому при анализе риска рассматривают одновременно сценарий атаки, последствия, доступные средства наблюдения и необходимые средства предупреждения.

## 6. Безопасная разработка — постоянный процесс

Безопасность появляется не только на этапе тестирования готовой системы. На стадиях проектирования и разработки нужны моделирование угроз, безопасные требования, проверка кода и зависимостей, управление секретами, настройки конфигурации, журналирование и план реагирования.

**Code review** оценивает реализацию и её контекст. **SAST** ищет потенциальные дефекты в коде/промежуточном представлении; **DAST** исследует работающую систему снаружи; анализ компонентов выявляет риски зависимостей; тестирование на проникновение проверяет реальные сценарии в установленной области. Ни один из методов не заменяет остальные и не гарантирует отсутствия уязвимостей.

| Механизм | Что он проверяет | Что не следует утверждать |
|---|---|---|
| Параметризованный SQL | Разделение структуры запроса и параметра | «Все классы инъекций исчезли» |
| Экранирование по контексту | Безопасность вывода данных в браузере | «Любой XSS невозможен» |
| Авторизация объекта | Право субъекта на конкретный ресурс | «Любой корректный токен даёт это право» |
| SAST/DAST | Определённые классы слабостей при условиях инструмента | «Отчёт доказывает полную безопасность» |

## 7. Мониторинг и реагирование: почему нужны разные источники

Представим три артефакта одного эпизода: Suricata зарегистрировала HTTP-запрос, приложение записало отказ в доступе, база данных не зафиксировала изменение данных. Совместный анализ уточняет допустимый вывод: был запрос, контроль доступа его отклонил, подтверждений успешного изменения записи нет. Однако отсутствие записи в журнале БД может зависеть от полноты аудита, поэтому вывод нужно соотносить с реальными условиями регистрации.

Типовой порядок расследования: установить область и время эпизода, сохранить оригинальные записи, связать по надёжным идентификаторам, проверить результат защитного механизма, отделить наблюдение от предположения. Утверждение «IDS зафиксировала атаку» часто требует уточнения: детектор зарегистрировал совпадение условия, а успех атаки устанавливается дополнительно.

## 8. Мини-кейс для самостоятельного анализа

Веб-приложение принимает запрос `GET /orders/42`, пользователь аутентифицирован, но должен видеть только собственные заказы. В журнале приложения появляется `403 Forbidden`, а NIDS фиксирует соответствующий HTTP-обмен.

**Что известно:** запрос обработан и отклонён согласно журналу приложения; отдельный сетевой источник зафиксировал трафик. **Что нужно уточнить:** действительно ли сервер проверил принадлежность объекта, все ли альтернативные API-методы защищены и можно ли связать сетевое событие именно с этим запросом.

Здесь студент должен сформулировать не только название уязвимости, но и конкретное необходимое свойство защиты — проверка авторизации на уровне объекта — и предложить как positive, так и negative тест.




## Дополнение: доверительные границы, защита данных и жизненный цикл

Безопасность приложения не сводится к поиску опасных строк в HTTP. Представьте сервис, который получает токен пользователя, открывает объект из базы и пишет результат в журнал. Здесь есть как минимум три разных решения: можно ли доверять **подлинности** токена; имеет ли субъект **право на этот объект**; должны ли данные объекта попадать в журнал и кто вправе их читать. Успех одной проверки не заменяет остальные. Например, валидный токен и ответ `200 OK` не доказывают корректную авторизацию на уровне конкретного объекта.

Для **CSRF** существенен сценарий, в котором браузер автоматически отправляет учётные данные или сеансовые cookie вместе с нежелательным запросом. Защитные механизмы включают проверяемые CSRF-токены, обоснованную политику SameSite и дополнительные проверки источника запроса с учётом особенностей приложения. Эти меры не заменяют авторизацию и не применяются одинаково ко всем API: модель риска отличается, если запросы аутентифицируются токеном, который браузер не прикрепляет автоматически.

**Шифрование при хранении** и **шифрование при передаче** закрывают разные угрозы. HTTPS защищает данные на сетевом участке до точки завершения TLS, но не шифрует автоматически строки базы данных или резервную копию. Шифрование носителя снижает риск при утрате носителя, однако запущенное приложение может получить расшифрованные данные от имени своей учётной записи. Поэтому необходимо разграничить полномочия, обеспечить защиту ключей и секретов, контролировать резервные копии и избегать записи чувствительных данных в журналы. Не следует хранить ключи в репозитории вместе с кодом или считать ротацию выполненной только по изменению конфигурационного файла.

### Проверяем безопасность на каждом этапе разработки

Начните с модели угроз: определите активы, акторов, границы доверия, возможные злоупотребления и предпосылки их выполнения. Затем формализуйте требования: например, *пользователь А не может читать заказ пользователя Б*, включая прямой запрос к API и повторное использование идентификатора. В коде реализуйте авторизацию на стороне сервера; при ревью проверьте ветви доступа; статическим анализом ищите соответствующие паттерны; динамически протестируйте разрешённый и запрещённый запрос. После выпуска мониторинг и журналы нужны для выявления отклонений, но **само оповещение IDS не доказывает эксплуатацию уязвимости**.

| Контроль | Типичная ошибка | Проверяемый результат |
|---|---|---|
| Параметризованный SQL-запрос | Конкатенация недоверенных данных в SQL | Входное значение остаётся параметром, а не частью структуры команды |
| Авторизация объекта | Проверка только факта входа | Доступ к чужому объекту запрещён сервером |
| Управление секретами | Ключ в исходном коде или журнале | Доступ ограничен, секрет не раскрывается через обычный вывод |
| Инцидентный мониторинг | Оповещение приравнивают к доказанной атаке | Сопоставлены вход, обработка, журнал и фактическое изменение состояния |

**Самостоятельное упражнение:** зафиксируйте для `GET /api/orders/42` два сценария — владелец и посторонний авторизованный пользователь. Для каждого укажите ожидаемый HTTP-ответ, проверку в приложении и источник доказательства. Не используйте один лишь статус сетевого IDS как результат теста авторизации.
