# Итоговый проект — проверяемая возможность обнаружения или предотвращения

Итоговый проект завершает СРО. Его цель — показать, что студент умеет не только настроить средство защиты, но и **доказать полученный результат на основе воспроизводимого evidence**.

## Формат проекта

Студент выбирает либо получает от преподавателя один **ограниченный и разрешённый** сценарий. Это может быть задача на обнаружение, наблюдаемость, корреляцию либо предотвращение.

Проект не обязан демонстрировать реальную компрометацию. Контролируемый marker, тестовое событие, безопасная имитация или подготовленный набор данных допустимы, если выводы сформулированы в пределах фактически полученного evidence.

## Обязательная структура

### 1. Scope и разрешённые действия

Определите:

- цель проекта;
- in scope / out of scope;
- разрешённые действия;
- запрещённые действия;
- stop conditions.

Техническая доступность цели сама по себе не означает разрешение на её тестирование.

### 2. Сценарий угрозы

Опишите:

```text
актив
→ угроза
→ уязвимость / условие
→ контролируемое действие
→ возможное последствие
```

Если используется учебный marker, так и называйте его. Не превращайте лабораторное совпадение условия в утверждение о реальной атаке.

### 3. Observation design

Для каждого используемого источника укажите:

| Что указать | Пример вопроса |
|---|---|
| Observation point | Где физически или логически наблюдается событие? |
| Источник данных | PCAP, EVE, audit, application log, endpoint telemetry и т. п. |
| Acquisition | Как данные были получены? |
| Representation | В каком виде система представила событие? |
| Доступные поля | Что реально можно анализировать? |
| Ограничения | Что этот источник не видит? |

### 4. Контролируемый эксперимент

Эксперимент должен быть воспроизводимым. Зафиксируйте:

- последовательность действий;
- команды/настройки, если они использовались;
- версии ПО;
- входные данные;
- время или идентификатор тестового запуска, если это помогает отделить его от старых событий.

### 5. Detection / prevention logic

Объясните, почему система должна принять решение. Допустимы, например:

- signature;
- state/protocol logic;
- threshold;
- anomaly;
- correlation;
- другая обоснованная логика.

Если заявляется prevention, отдельно покажите:

```text
detection
→ решение
→ enforcement
→ фактический результат
```

`alert` сам по себе не доказывает блокирование.

### 6. Raw evidence

Проект должен содержать минимум один первичный артефакт, который другой человек может проверить:

- EVE/лог;
- PCAP;
- host audit/event;
- application log;
- endpoint telemetry;
- иной воспроизводимый источник.

Скриншот интерфейса может дополнять evidence, но не заменяет исходный артефакт.

### 7. Проверка качества

Минимально проверьте три случая:

| Проверка | Назначение |
|---|---|
| Positive case | ожидаемое условие действительно срабатывает |
| Negative case | похожее, но допустимое событие не должно давать тот же результат |
| Boundary case | поведение около границы условия понятно и воспроизводимо |

Если есть ground truth, можно дополнительно использовать TP/FP/TN/FN и подходящие метрики.

### 8. Интерпретация и ограничения

Отдельно ответьте:

- что результат **доказывает**;
- чего он **не доказывает**;
- где возможны FP/FN;
- какие blind spots остаются;
- какие дополнительные данные усилили бы вывод.

### 9. Коммуникация результата

Подготовьте два представления одной работы:

**Техническое:** ход эксперимента, конфигурация, evidence, анализ и ограничения.

**Краткое:** понятное резюме для человека, которому не нужны все технические детали, но важно понять результат, риск и ограничения.

Оба представления должны описывать один и тот же фактический результат без завышения уверенности.

### 10. Воспроизводимость

В приложении укажите всё, что необходимо для повторения работы:

- версии ПО;
- конфигурации;
- команды;
- входные данные;
- расположение evidence;
- контрольные суммы собственных пакетов/артефактов, если они создавались.

## Рекомендуемая структура сдаваемого комплекта

```text
project/
├── README.md            # цель, scope и порядок воспроизведения
├── report.md или .pdf   # основной отчёт
├── evidence/            # первичные артефакты
├── config/              # изменённые конфигурации / правила
└── hashes.txt           # контрольные суммы, если применимо
```

Формат файлов может быть изменён преподавателем, но логика `report → evidence → reproducibility` должна сохраняться.

## Критерии готовности проекта

Проект готов к сдаче, если другой человек может пройти цепочку:

```text
scope
→ action
→ trace
→ observation point
→ acquisition
→ representation
→ detection / prevention result
→ interpretation
```

и для каждого перехода найти конкретное подтверждение.

Работа требует доработки, если:

- вывод сильнее имеющегося evidence;
- `alert` выдан за доказанную атаку или предотвращение;
- отсутствует raw evidence;
- эксперимент невозможно повторить по описанию;
- не показаны ограничения;
- положительный результат проверен, а negative/boundary cases отсутствуют.

## Финальный checklist

Перед сдачей убедитесь:

- [ ] scope сформулирован;
- [ ] контролируемое действие воспроизводимо;
- [ ] источники и observation points описаны;
- [ ] raw evidence сохранён;
- [ ] detection/prevention logic объяснена;
- [ ] positive, negative и boundary cases выполнены;
- [ ] выводы не сильнее evidence;
- [ ] ограничения указаны;
- [ ] технический и краткий результаты согласованы;
- [ ] другой человек сможет повторить проверку.
