# Итоговый проект — проверяемая возможность обнаружения/предотвращения

Проект завершает СРО и связывает теорию, практику и evidence discipline курса.

## Задача

Выберите или получите от преподавателя один **ограниченный и разрешённый** сценарий. Спроектируйте и проверьте возможность обнаружения или предотвращения так, чтобы другой человек мог воспроизвести эксперимент и проверить ваш вывод.

## Обязательные части

### 1. Scope и разрешение

Определите:
- цель;
- in scope / out of scope;
- разрешённые действия;
- stop conditions.

Используйте принципы из практического блока A.

### 2. Сценарий угрозы

Опишите:

```text
актив
→ угроза
→ уязвимость / условие
→ контролируемое действие
→ возможное последствие
```

Не называйте лабораторный marker «реальной атакой», если этого не подтверждает эксперимент.

### 3. Observation design

Укажите:
- observation point;
- источник данных;
- способ получения;
- representation;
- поля, которые реально доступны анализу.

### 4. Контролируемый эксперимент

Эксперимент должен быть воспроизводимым. Сохраните команды, конфигурацию, версии и входные данные.

### 5. Detection / prevention logic

Покажите, на каком основании принимается решение: signature, состояние, threshold, anomaly, correlation или другое обоснованное условие.

Если заявляется prevention, отдельно докажите enforcement. `alert` сам по себе не доказывает блокирование.

### 6. Raw evidence

Минимум один первичный артефакт:
- EVE/лог;
- PCAP;
- host audit/event;
- application log;
- другой воспроизводимый источник.

Скриншот интерфейса может дополнять raw evidence, но не заменяет его.

### 7. Проверка качества

Минимум:
- positive case;
- negative case;
- boundary case.

Если есть ground truth, используйте подходящие метрики и не подменяйте ими инженерное объяснение.

### 8. Ограничения

Отдельно напишите:
- что результат доказывает;
- чего он не доказывает;
- где возможны FP/FN или blind spots.

### 9. Отчёт и коммуникация

Сдайте два представления одного результата:
1. технический отчёт с evidence;
2. краткое резюме для руководителя/заказчика без лишнего жаргона и без завышения выводов.

### 10. Reproducibility appendix

Укажите:
- версии ПО;
- конфигурации;
- команды;
- входные данные;
- контрольные суммы собственных пакетов/артефактов, если они создавались.

## Минимальный критерий успешного проекта

Проект считается завершённым, когда преподаватель может пройти цепочку:

```text
scope
→ action
→ trace
→ observation
→ evidence
→ detection/prevention result
→ interpretation
```

и для каждого перехода увидеть конкретное подтверждение.
