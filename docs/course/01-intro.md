# Глава 1. Что такое IDS/IPS и зачем они нужны

<div class="chapter-lead">
<p>Информационная система уже защищена межсетевым экраном. Из внешней сети разрешён доступ только к публичному веб-сервису, остальные ненужные взаимодействия запрещены.</p>
<p>Но остаётся вопрос: <strong>что произойдёт, если нежелательная активность будет использовать именно тот путь, который системе необходимо оставить доступным?</strong></p>
</div>

<div class="chapter-outcomes">
<strong>После изучения главы студент должен уметь:</strong>
<p>объяснить назначение IDS и IPS; отличить detection от prevention; объяснить, почему firewall и IDS/IPS решают разные защитные задачи; на базовом уровне отличить WAF от IDS/IPS; объяснить, почему alert сам по себе ещё не означает компрометацию.</p>
</div>

## 1. Сначала обычная информационная система

Рассмотрим упрощённый фрагмент инфраструктуры:

```text
Internet
   │
   ▼
Firewall
   │
   ▼
Web Server
```

Веб-сервер должен быть доступен пользователям. Поэтому полностью запретить обращения к нему нельзя.

Политика доступа может выглядеть так:

```text
Internet → Web Server      ALLOW
Internet → Database        DENY
Internet → SSH Management  DENY
```

Если взаимодействие не требуется для работы системы, его следует ограничить политикой доступа, а не оставлять открытым в надежде, что IDS обнаружит каждую попытку атаки.

Но разрешённый веб-сервис всё равно остаётся доступным для взаимодействия.

Первое фундаментальное отношение курса:

```text
ALLOWED ≠ SAFE
```

Разрешённое взаимодействие не обязательно является безопасным взаимодействием.

---

## 2. Какую задачу решает firewall

**Firewall** контролирует прохождение сетевого трафика в соответствии с установленной политикой безопасности.

Важно не сводить его работу к формуле:

```text
Firewall = IP + Port
```

Простейшие механизмы фильтрации действительно могут принимать решения на основании адресов, протокола, портов и направления. Stateful firewall также учитывает состояние соединения, поэтому ответный трафик установленной допустимой сессии рассматривается в контексте этого соединения.

Современные NGFW могут учитывать ещё больше признаков: приложения, пользователей и свойства прикладных протоколов.

Поэтому противопоставление

```text
Firewall = L3/L4
IDS = L7
```

некорректно.

Упрощённо главный вопрос firewall можно сформулировать так:

> **Допустимо ли данное сетевое взаимодействие согласно установленной политике?**

Например, взаимодействие `Internet → Database:5432` может быть запрещено вообще, независимо от того, содержит ли оно атаку. А обращение к публичному веб-сервису может быть разрешено, потому что без него система не выполняет свою функцию.

## 3. Где возникает задача обнаружения

!!! note "Учебная модель / синтетический сценарий"
    В этой главе намеренно используется обычный HTTP без TLS. Это позволяет рассмотреть различие между контролем доступа и обнаружением, не вводя пока вопрос доступности зашифрованного содержимого.

Схема:

```text
Client ─────► Firewall ─────► Web Server
               ALLOW
             TCP/8080
```

Обычный запрос:

```http
GET /lab-test HTTP/1.1
Host: web.lab
```

И другой запрос:

```http
GET /admin-test?marker=ATTACK-LAB HTTP/1.1
Host: web.lab
```

С точки зрения рассмотренной сетевой политики оба запроса используют разрешённое взаимодействие с опубликованным сервисом.

Мы не предполагаем, что firewall ничего не умеет анализировать кроме номера порта. В конкретной инфраструктуре он может обладать дополнительными функциями инспекции.

Но сам факт разрешённости взаимодействия не отвечает на другой вопрос:

> **Содержит ли наблюдаемая активность признаки, которые система безопасности должна обнаружить?**

Это уже задача intrusion detection.

---

## 4. Что такое IDS

**IDS — Intrusion Detection System — система обнаружения вторжений.**

В общем виде IDS получает доступные ей сведения о происходящей активности и анализирует их на наличие заданных признаков возможных инцидентов или иной security-relevant activity.

Для первой главы достаточно модели:

```text
Наблюдаемая активность
        │
        ▼
       IDS
        │
        ▼
    Анализ данных
        │
        ▼
 Detection result
```

Ключевое выражение — **«доступные системе данные»**.

IDS не обладает абсолютной наблюдаемостью. Что именно она сможет получить, зависит от типа системы, места размещения, способа получения данных, шифрования и конфигурации.

Эти ограничения мы будем разбирать постепенно.

---

## 5. Event и Alert — не одно и то же

Система может создавать различные записи о наблюдаемой активности: соединение установлено, DNS-запрос получен, процесс запущен, файл изменён и т. д.

Для курса используем простое различие:

**Event** — зафиксированное системой событие или результат наблюдения.

**Alert** — выделенный результат обнаружения, означающий, что наблюдаемая активность удовлетворила некоторому условию, которое требует внимания или дальнейшей обработки.

Конкретные продукты могут использовать термины `event`, `alert`, `finding` и `detection` по-разному. Сейчас нам важно различать:

```text
что-то произошло
       ≠
детектор посчитал это security-relevant
```

---

## 6. Что означает Alert

Добавим к стенду пассивный сетевой сенсор:

```text
Client ─────► Firewall ─────────────► Web Server
                              │
                              │ копия доступного трафика
                              ▼
                            NIDS
```

Основной трафик идёт к серверу. В нашем примере NIDS получает копию доступного ему сетевого трафика и не является обязательной транзитной точкой.

Как именно создаётся такая копия, будет разобрано в Главе 4.

Пусть detector ищет маркер `ATTACK-LAB` в определённом поле HTTP-запроса. При получении запроса

```http
GET /admin-test?marker=ATTACK-LAB HTTP/1.1
Host: web.lab
```

он формирует:

```text
ALERT
Suspicious Lab Marker Detected
```

Что действительно подтверждено?

> В анализируемом системой представлении запроса присутствовал признак, удовлетворивший условию detector.

Но из этого ещё не следует, что приложение уязвимо, эксплуатация была успешной, атакующий получил доступ или сервер был скомпрометирован.

Второе фундаментальное отношение:

```text
ALERT ≠ COMPROMISE
```

---

## 7. Что такое IPS

**IPS — Intrusion Prevention System — система предотвращения вторжений.**

Она выполняет detection и дополнительно может инициировать действие, направленное на предотвращение или прекращение обнаруженной нежелательной активности.

Простейшая сетeвая модель:

```text
Client ─────► IPS ─────► Server
               │
               ├── разрешить передачу
               └── применить prevention action
```

Но не следует запоминать:

```text
IDS = сбоку
IPS = inline
```

Это смешивает две разные характеристики: **как система получает данные** и **может ли она инициировать воздействие**.

Inline-система может работать в режиме `alert-only`. А пассивный detector в некоторых архитектурах может инициировать действие через другой control, например firewall API.

Для первой главы достаточно:

```text
IDS → обнаружение
IPS → обнаружение + возможность предотвращения
```

Третье фундаментальное отношение:

```text
DETECTION ≠ PREVENTION
```

---

## 8. Почему ошибка prevention имеет другую цену

Если detector ошибочно выделил легитимную активность как нежелательную, в alert-only режиме это может привести к лишнему оповещению и дополнительной проверке.

Если то же решение автоматически связано с prevention action, последствия могут затронуть уже саму систему: легитимный пакет может быть отброшен, сессия прервана, пользователь не получит услугу, бизнес-процесс будет нарушен.

Это не означает, что IPS «опасен». Вывод другой:

> **Автоматическое предотвращение требует более строгой проверки detection logic и понимания последствий ошибочного воздействия.**

FP/FN и методы такой проверки появятся позднее, когда у студента уже будет базовая модель IDS/IPS.

---

## 9. Firewall и IDS/IPS не заменяют друг друга

Если внешний SSH-доступ не требуется, правильное решение — запретить его политикой доступа:

```text
Internet → Server:22  DENY
```

IDS/IPS не должна подменять возможность устранить ненужный сетевой путь.

Но если публичный сервис должен обслуживать клиентов, некоторый набор взаимодействий необходимо разрешить. После этого остаётся задача наблюдения за security-relevant activity внутри доступной системе области.

Поэтому firewall и IDS/IPS решают разные, но дополняющие друг друга задачи.

---

## 10. Функция и продукт — разные вещи

Firewall и IPS не обязательно являются двумя отдельными устройствами.

Одна NGFW-платформа может совмещать несколько функций:

```text
firewall policy
IPS
application identification
URL filtering
logging
...
```

Поэтому необходимо отличать **физический продукт** от **защитной функции**.

Если IPS встроена в NGFW, intrusion prevention никуда не исчезла — она реализована внутри той же платформы.

Четвёртое фундаментальное отношение:

```text
FIREWALL ≠ IDS/IPS
```

Это не утверждение о количестве устройств. Это различие защитных задач.

---

## 11. А где здесь WAF

**WAF — Web Application Firewall** — специализированное средство защиты веб-приложений и связанного с ними web-трафика.

WAF может анализировать HTTP-запросы и ответы и применять политики защиты веб-приложения на основании доступных ему элементов web transaction.

Сетевой IDS/IPS может работать не только с HTTP, но и с другими доступными ему сетевыми протоколами и видами активности. Host-based IDS получает другой класс данных — события на самом узле.

Базовая модель:

```text
WAF
→ специализирован на защите web-приложений

IDS/IPS
→ класс систем обнаружения / предотвращения вторжений
  с различными источниками данных
```

Возможности могут пересекаться. WAF и NIDS могут одновременно анализировать один HTTP-запрос и обнаружить в нём один и тот же интересующий признак.

Правильный вывод: это разные классы защитных средств с частично пересекающимися возможностями.

## 12. Соберём пример целиком

```text
                  [ SYNTHETIC LAB MODEL ]

Client ─────► Firewall ─────────────────► Web Server
                │                            :8080
                │ ALLOW
                │
                └──────── основной traffic path

                              │
                              │ passive copy
                              ▼
                            NIDS
                              │
                              ▼
                            ALERT
```

Клиент отправляет:

```http
GET /admin-test?marker=ATTACK-LAB HTTP/1.1
Host: web.lab
```

Firewall применяет policy и допускает взаимодействие с опубликованным сервисом. NIDS получает доступную ему копию сетевой активности. Detection condition совпадает с признаком `ATTACK-LAB`, и система формирует alert.

Подтверждено:

> detector получил достаточное представление запроса и его условие выполнилось.

Не подтверждено:

> кто именно отправил запрос, уязвимо ли приложение, привёл ли запрос к нежелательному результату и была ли система скомпрометирована.

---

## 13. Четыре идеи первой главы

```text
ALLOWED ≠ SAFE
FIREWALL ≠ IDS/IPS
DETECTION ≠ PREVENTION
ALERT ≠ COMPROMISE
```

Если эти четыре отношения понятны, первая глава выполнила свою задачу.

## Источники и статус утверждений

- NIST SP 800-94, *Guide to Intrusion Detection and Prevention Systems (IDPS)* — фундаментальные определения IDS/IPS и функций detection/prevention. Документ используется как исторический foundational source, а не как описание современных продуктов.
- NIST SP 800-41 Rev.1, *Guidelines on Firewalls and Firewall Policy* — базовая роль firewall и stateful filtering.
- Учебный HTTP-сценарий `ATTACK-LAB` — **SYNTHETIC**, создан специально для курса и не является реальным exploit/case.
