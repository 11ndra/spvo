# Глава 2. Что система может видеть: источники данных и классы IDPS

<div class="chapter-lead">
<p>В первой главе мы пришли к важному выводу: система обнаружения полезна только тогда, когда получает именно те данные, в которых остаются следы интересующей нас активности.</p>

<p>Теперь представим реальный инцидент. Пользователь открывает вредоносный документ. ## 1. Начнём с понятия «источник данных»

Система обнаружения не видит «атаку» как абстрактное понятие. Она видит только **наблюдаемые данные**.

Если пользователь запустил подозрительную программу, след может появиться в событиях операционной системы. Если эта программа начала устанавливать соединения, след появится в сети. Если она изменила файл, это можно обнаружить на самом хосте. Если рядом возникла чужая точка Wi‑Fi, её присутствие проявляется уже в радиоэфире.

Для всех таких наблюдаемых данных удобно использовать термин **телеметрия (telemetry)** — данные о состоянии и действиях системы, которые можно собирать и анализировать.

Для инженера вопрос выбора IDS/IPS фактически начинается так:

> **Где именно останется наблюдаемый след той угрозы, которую я хочу обнаруживать?**

Только после этого имеет смысл выбирать класс системы и инструмент.

## 3. Сетевая система: наблюдаем взаимодействие между узлами

Система, которая анализирует сетевые данные, называется **сетевой системой обнаружения или предотвращения вторжений (Network-based IDS/IPS, NIDS/NIPS)**.

Вместо того чтобы устанавливать агент на каждый компьютер, сетевой сенсор получает трафик из определённой точки инфраструктуры и анализирует взаимодействие множества узлов.

### Что она получает

На базовом уровне сетевой сенсор работает с пакетами. Из них он может восстановить более содержательные сущности:

```text
пакеты
   ↓
сетевой поток
   ↓
TCP-соединение
   ↓
прикладной протокол
   ↓
HTTP / DNS / TLS / ...
```

Из такого взаимодействия можно получить:

- кто с кем связывается;
- по какому протоколу;
- на какой порт;
- сколько данных передано;
- как долго длится соединение;
- какие прикладные сообщения доступны анализу;
- соответствует ли активность известной сигнатуре или правилу.

### Что происходит под капотом

Сетевой сенсор не обязан рассматривать каждый пакет изолированно. Он сопоставляет пакеты между собой, определяет направления взаимодействия и восстанавливает состояние соединений.

В следующих главах мы отдельно разберём:

```text
получение пакетов
→ декодирование
→ отслеживание потока
→ восстановление TCP
→ разбор протокола
→ логика обнаружения
```

Пока достаточно понять главное: **NIDS анализирует сетевой след события**.

### Что настраивает инженер

Реальная настройка сетевой системы обычно включает гораздо больше, чем включение набора сигнатур. Инженер должен определить:

- какие сегменты являются защищаемыми;
- откуда сенсор получает трафик;
- какие протоколы необходимо анализировать;
- какие правила применимы к этой инфраструктуре;
- какие события сохранять;
- какие объёмы нагрузки должна выдерживать система;
- требуется ли только обнаружение или допустимо автоматическое предотвращение.

Позже эти параметры мы будем настраивать практически.

### Что NIDS не знает сама по себе

Предположим, сенсор увидел:

```text
10.10.20.15 → 10.10.30.10:445
```

Он может определить подозрительную сетевую активность.

Но из одного сетевого события не всегда можно сказать:

> какой именно процесс на `10.10.20.15` инициировал соединение?

Для этого нужен источник данных с самого узла.

## 4. Хостовая система: смотрим внутрь сервера или рабочей станции

**Хостовая система обнаружения или предотвращения вторжений (Host-based IDS/IPS, HIDS/HIPS)** получает данные непосредственно с защищаемого компьютера.

Обычно для этого на хост устанавливается программный компонент — **агент**. Его задача заключается не в том, чтобы «знать все атаки», а в том, чтобы собирать необходимые события и передавать их механизмам анализа.

### Какие следы есть на хосте

Операционная система знает то, чего сетевой сенсор обычно не знает:

- какой пользователь вошёл в систему;
- какой процесс был запущен;
- какой процесс породил другой процесс;
- какой файл был создан или изменён;
- изменились ли права доступа;
- произошла ли неуспешная аутентификация;
- какие системные события зарегистрированы.

Рассмотрим изменение файла:

```text
/etc/ssh/sshd_config
```

Сетевая система может вообще не увидеть момент изменения.

Хостовая система способна зафиксировать:

```text
файл изменён
время: 14:32:08
старое состояние: ...
новое состояние: ...
контекст пользователя/процесса: ...
```

### Контроль целостности файлов

Одним из распространённых механизмов является **контроль целостности файлов (File Integrity Monitoring, FIM)**.

Идея проста: система знает ожидаемое состояние важных файлов и проверяет, не изменилось ли оно.

Это не означает, что каждое изменение вредоносно. Конфигурационный файл может законно изменить администратор. Поэтому событие изменения снова является **сигналом для интерпретации**, а не готовым доказательством атаки.

### Что настраивает инженер

Для хостовой системы требуется решить:

- на каких узлах нужен агент;
- какие журналы операционной системы собирать;
- какие каталоги и файлы контролировать;
- какие изменения являются ожидаемыми;
- какие события исключать;
- сколько телеметрии допустимо создавать;
- как агент связывается с серверной частью системы.

Неправильный выбор объектов мониторинга способен создать огромный поток бесполезных событий или, наоборот, оставить критичную область без наблюдения.

## 5. Беспроводная система: сеть начинается не с кабеля

Теперь представим офис, в котором вся серверная сеть хорошо контролируется. На периметре есть межсетевой экран, сетевые сенсоры получают нужный трафик, на важных серверах установлены агенты.

Но злоумышленник включает рядом с офисом точку доступа:

```text
SSID: Corp-WiFi
```

с тем же именем, что и легитимная сеть.

Проводная IDS сама по себе не является полноценным средством наблюдения за радиоэфиром.

Для этого используется **беспроводная система обнаружения или предотвращения вторжений (Wireless IDS/IPS, WIDS/WIPS)**.

### Почему это отдельный класс

Wi‑Fi содержит собственные объекты и механизмы:

- радиоканалы;
- точки доступа;
- идентификаторы беспроводных сетей;
- служебные кадры стандарта 802.11;
- подключение и отключение клиентов;
- особенности аутентификации.

Чтобы наблюдать эту среду, система должна получать соответствующие беспроводные кадры.

### Что она способна искать

Например:

- неизвестные точки доступа;
- точки с корпоративным именем сети, но неизвестным идентификатором;
- запрещённые беспроводные сети;
- необычные служебные кадры;
- нарушения корпоративной политики Wi‑Fi.

### Что настраивает инженер

Настройка WIDS начинается не с «включить все правила», а с описания нормальной беспроводной среды:

- какие точки доступа принадлежат организации;
- какие сети разрешены;
- какие каналы используются;
- где физически находятся сенсоры;
- какие события считаются нарушением политики.

Здесь особенно хорошо видно, почему **baseline нормального состояния** важен для обнаружения.

## 6. Анализ сетевого поведения: когда важна не строка, а закономерность

Представим, что вредоносная программа каждые 60 секунд устанавливает короткое зашифрованное соединение наружу.

Содержимое соединения недоступно анализу, и известной сигнатуры нет.

Но сама последовательность выглядит необычно:

```text
12:00:00 → external host
12:01:01 → external host
12:02:00 → external host
12:03:02 → external host
```

Отдельное соединение может выглядеть нормальным.

Подозрительным становится **поведение во времени**.

Такой подход лежит в основе систем и методов **анализа сетевого поведения**. В современной терминологии можно встретить названия **Network Traffic Analysis (NTA)** и **Network Detection and Response (NDR)**. В старых источниках, включая классические руководства, встречается термин **Network Behavior Analysis (NBA)**.

### Что анализируется

Вместо полного содержимого пакетов часто используются характеристики взаимодействия:

- источник и назначение;
- частота соединений;
- длительность;
- объём переданных данных;
- повторяемость;
- появление новых узлов взаимодействия;
- отклонение от привычной картины.

### Почему это не «магический искусственный интеллект»

Поведенческий анализ не означает:

> система сама поймёт любую новую атаку.

Он всё равно зависит от качества данных, корректного baseline, выбранных признаков и допустимого уровня ложных срабатываний.

Если в компании каждую ночь запускается резервное копирование и создаёт огромный скачок трафика, система должна учитывать, что это нормальное поведение.

### Что делает инженер

Инженеру необходимо определить:

- какие сети анализируются;
- какие данные о соединениях доступны;
- что считается нормальным для конкретного сегмента;
- какие отклонения действительно представляют интерес;
- как учитывать расписания и бизнес-процессы;
- как подтверждать аномалию другими источниками.

## 7. Принципиальное отличие классов: точка наблюдения

Теперь можно отказаться от запоминания четырёх аббревиатур и сформулировать гораздо более полезное правило.

<div class="chapter-summary">
  <span>Ключевая идея</span>
  <p>Класс IDPS определяется прежде всего тем, <strong>откуда система получает наблюдаемые данные</strong>. Сетевой сенсор видит сетевой след, хостовый агент — события конкретного узла, беспроводной сенсор — радиоэфир, а поведенческий анализ — закономерности сетевых взаимодействий.</p>
</div>

Это означает, что вопрос:

> «Какая IDS лучше?»

почти всегда поставлен неправильно.

Правильнее спросить:

> **Что я хочу обнаружить и в каком источнике данных останется наиболее полезный след?**

## 8. Сравним одну атаку с четырёх точек наблюдения

Предположим, атакующий получил возможность выполнить команду на веб-сервере. После этого он создал файл, запустил процесс и установил соединение с внешним узлом.

| Что произошло | Сетевая система | Хостовая система | Беспроводная система | Анализ поведения |
|---|---:|---:|---:|---:|
| Входящий подозрительный запрос | хорошо | зависит от журналов приложения | нет | частично |
| Создан новый процесс | обычно нет | хорошо | нет | нет напрямую |
| Изменён системный файл | обычно нет | хорошо | нет | нет |
| Сервер связался с новым внешним узлом | хорошо | может видеть локально | нет | хорошо |
| Соединение повторяется каждые 60 секунд | может видеть | может видеть локально | нет | особенно полезно |
| Появилась rogue Wi‑Fi AP | нет | нет | хорошо | обычно нет |

Таблица показывает ещё одну важную вещь: области видимости **перекрываются**.

Это полезно.

Если сетевой сенсор сообщил о подозрительном соединении, а хостовый агент одновременно зарегистрировал запуск неожиданного процесса, два независимых наблюдения усиливают контекст расследования.

## 9. Почему нельзя просто поставить всё сразу

Может показаться, что решение очевидно:

> установим все возможные сенсоры и будем собирать всё.

В реальной инфраструктуре это приводит к новым проблемам.

Чем больше источников данных, тем больше:

- объём хранения;
- нагрузка на сеть и серверы;
- количество событий;
- сложность настройки;
- потребность в сопровождении;
- риск информационного шума.

Поэтому зрелая архитектура наблюдения начинается не с максимального сбора данных, а с вопроса:

> **Какая телеметрия нужна для конкретных сценариев угроз и решений специалиста?**

Например, нет смысла непрерывно контролировать изменение каждого временного файла операционной системы, если эти события не помогают решать задачу безопасности.

То же относится к сети: собирать абсолютно весь трафик недостаточно. Нужно понимать, **какие сетевые пути важны и зачем мы их наблюдаем**.

## 10. Как инженер выбирает подходящий класс IDPS

Представим, что вам поручили защитить новую систему.

Начинать с выбора продукта рано.

Сначала последовательно задаются вопросы.

  <div class="pipeline-step">

    <div>
      <strong>Какой след оставляет это действие?</strong>
      <p>Пакет, запись системного журнала, изменение объекта, беспроводной кадр или изменение поведения?</p>
    </div>
  </div>

  <div class="pipeline-step">
    <span>4</span>
    <div>
      <strong>Где этот след можно наблюдать?</strong>
      <p>На сетевой границе, внутри сегмента, непосредственно на хосте или в радиоэфире?</p>
    </div>
  </div>

  <div class="pipeline-step">
    <span>5</span>
    <div>
      <strong>Какая система способна получить эти данные?</strong>
      <p>Только теперь появляется осмысленный выбор NIDS/NIPS, HIDS/HIPS, WIDS/WIPS или поведенческого анализа.</p>
    </div>
  </div>

</div>

Это универсальный инженерный алгоритм, который будет использоваться на протяжении всего курса.

## 12. Профессиональный сценарий: расследование без туннельного зрения

Допустим, сетевой сенсор сообщает:

```text
Internal host → unusual external destination
```

Слабый подход:

> IDS сказала, что это атака.

Более профессиональный подход начинается с уточнения контекста.

Сетевой сигнал отвечает на вопрос:

> какой узел и куда установил соединение?

Но для расследования могут потребоваться другие источники:

```text
Хостовая телеметрия:
какой процесс инициировал соединение?

Данные аутентификации:
какой пользователь работал на узле?

Поведенческие данные:
появлялось ли такое соединение раньше?

Контекст актива:
что это вообще за компьютер?
```

Таким образом, хороший специалист не пытается заставить один сенсор отвечать на все вопросы.

Он понимает **границы каждого источника данных** и комбинирует их тогда, когда это необходимо.
