# Глава 5. Как IDS/IPS встраивается в общую архитектуру защиты

<div class="chapter-lead">
<p>К этому моменту мы уже знаем, откуда IDPS получает данные, как эти данные обрабатываются и какими способами система решает, что событие подозрительно. Теперь возникает архитектурный вопрос: <strong>если в сети уже есть межсетевой экран, зачем нужен ещё один механизм контроля?</strong></p>

<p>Ответ нельзя свести к фразе «firewall работает на L3/L4, а IDS — на L7». Современные межсетевые экраны умеют гораздо больше. Полезнее разделять не устройства, а <strong>решения, которые инфраструктура принимает над трафиком</strong>.</p>
</div>

<div class="chapter-outcomes">
<strong>После этой главы вы должны уметь объяснить:</strong>
<p>чем решение о разрешении соединения отличается от анализа разрешённой активности; почему IDS/IPS не заменяет межсетевой экран и наоборот; как меняется картина при использовании NGFW; почему сначала уменьшают поверхность атаки, а затем добавляют детектирование; и как инженер распределяет функции защиты между несколькими механизмами.</p>
</div>

## 1. Одно соединение — несколько разных вопросов

Представим публичный веб-сервис.

Клиенты из Интернета должны иметь возможность обращаться к нему по HTTPS:

```text
Internet → Web Server : TCP/443
```

Первый вопрос инфраструктуры:

> **Разрешено ли такое соединение политикой?**

Если ответ «нет», соединение не должно проходить дальше.

Но если ответ «да», появляется второй вопрос:

> **Что происходит внутри уже разрешённого взаимодействия?**

Обычный пользователь и злоумышленник могут обращаться к одному серверу, на один порт и по одному протоколу. Разница проявится не обязательно в факте соединения, а в действиях внутри него.

Это и есть фундаментальное различие, вокруг которого строится глава.

## 2. Межсетевой экран прежде всего ограничивает доступ

**Межсетевой экран (firewall)** применяет политику к сетевым взаимодействиям.

В простом случае политика может выглядеть так:

```text
Internet → Web:443       ALLOW
Internet → Web:22        DENY
Internet → Database:5432 DENY
Web → Database:5432      ALLOW
```

Здесь уже реализуется очень сильный защитный принцип.

База данных не должна быть доступна напрямую из Интернета. Значит, лучше не пытаться обнаруживать атаки на публично открытый PostgreSQL, а **вообще не предоставлять атакующему такой сетевой путь**.

Это уменьшение **поверхности атаки (attack surface)** — количества доступных злоумышленнику возможностей взаимодействовать с системой.

Поэтому хороший архитектурный порядок начинается так:

> **Если доступ не нужен бизнесу — его нужно запретить, а не компенсировать наличием IDS.**

IDPS особенно полезна там, где взаимодействие необходимо разрешить и полностью устранить риск простым запретом невозможно.

---

## 3. Что добавляет IDS/IPS после разрешения доступа

Вернёмся к HTTPS.

Публичный сайт невозможно защитить правилом:

```text
Internet → Web:443 DENY
```

потому что тогда исчезнет сам сервис.

Поэтому соединение разрешается, но остаётся риск того, что через разрешённый канал придёт:

- попытка эксплуатации уязвимости;
- необычная последовательность протокольных действий;
- известный вредоносный признак;
- подозрительное сетевое поведение.

Именно здесь IDPS добавляет второй уровень контроля.

Межсетевой экран уже решил:

> этому взаимодействию **разрешено существовать**.

IDPS пытается ответить:

> это взаимодействие **выглядит допустимым с точки зрения безопасности или содержит признаки угрозы**?

Важно, что это разные задачи.

---

## 4. Почему IDS/IPS не заменяет firewall

Представим, что организация оставила SSH открытым всему Интернету:

```text
Internet → Server:22 ALLOW
```

и рассчитывает на IDS, которая будет сообщать о brute-force и подозрительных попытках входа.

Это слабая архитектура, если публичный SSH вообще не нужен.

IDS может:

- не иметь подходящего правила;
- потерять часть трафика;
- не распознать новую технику;
- создать alert слишком поздно;
- быть временно недоступной.

Если ненужное соединение было запрещено раньше, значительная часть этой проблемы просто не возникла бы.

Поэтому:

> **detetection не должна использоваться как замена возможности убрать ненужный сетевой доступ.**

Сначала ограничивается доступ. Затем контролируется то, что действительно должно оставаться разрешённым.

---

## 5. Почему firewall тоже не заменяет IDS/IPS

Теперь противоположная ситуация.

Порт 443 нужен и разрешён. Соединение соответствует политике. Состояние TCP корректно. Пользователь обращается именно к разрешённому серверу.

Но HTTP-запрос содержит попытку эксплуатации приложения.

Базового решения:

```text
src = Internet
dst = Web
port = 443
policy = allow
```

недостаточно, чтобы определить смысл запроса.

Современный firewall может обладать дополнительными механизмами анализа, поэтому нельзя утверждать, что любой firewall смотрит только на IP и порт. Однако логическая задача всё равно сохраняется:

> **разрешение доступа и обнаружение угроз — разные функции, даже если физически они реализованы одним устройством.**

---

## 6. А что меняется с NGFW?

**Межсетевой экран следующего поколения (Next-Generation Firewall, NGFW)** обычно объединяет несколько механизмов в одном продукте.

В зависимости от реализации это могут быть:

```text
stateful firewall
application identification
URL filtering
TLS inspection
IPS
malware detection
identity-aware policies
```

Поэтому схема:

```text
Firewall → отдельный IPS
```

не является обязательной физической архитектурой.

Иногда функции выглядят так:

```text
           ┌─────────────────────────┐
Traffic →  │          NGFW           │  → Application
           │                         │
           │ access policy           │
           │ application control     │
           │ IPS inspection          │
           │ TLS inspection          │
           └─────────────────────────┘
```

Но для инженера всё равно полезно мысленно разделять происходящие внутри решения.

Если пользователь жалуется, что соединение не проходит, причина может находиться:

- в сетевой политике;
- в application control;
- в IPS-правиле;
- в TLS inspection;
- в другом механизме.

Физически «коробка» одна, но диагностика требует понимать отдельные функции.

## 7. Эшелонированная защита: один механизм компенсирует ограничения другого

Подход, при котором безопасность строится из нескольких независимых или частично независимых уровней, называют **эшелонированной защитой (defense in depth)**.

Рассмотрим публичное веб-приложение.

Сначала межсетевой экран ограничивает доступ только необходимыми сетевыми путями.

Затем трафик может анализироваться средствами IDS/IPS.

Для специфических атак на веб-приложение может использоваться **межсетевой экран веб-приложений (Web Application Firewall, WAF)**, который понимает HTTP-контекст и политику конкретного приложения.

На сервере остаётся хостовая телеметрия, позволяющая понять, что произошло уже внутри операционной системы.

  </div>

  <div>

    <strong>IDS / IPS</strong>

  </div>

  <div>
    <span>3</span>

  </div>

  </div>

</div>

Эта схема не означает, что каждой организации обязательно нужны четыре отдельных продукта.

Она показывает **разные функции наблюдения и контроля**, которые могут быть распределены между разными технологиями.

## 8. Как инженер проектирует такую защиту

Полезно идти от бизнеса к технологии.

Сначала определяется, какие взаимодействия действительно необходимы.

Затем всё ненужное запрещается на уровне сетевой политики и сегментации.

После этого остаётся набор разрешённых взаимодействий, которые всё ещё несут риск. Для них инженер определяет, где требуется дополнительное обнаружение или предотвращение.

Логика выглядит так:

```text
Какой сервис нужен бизнесу?
        ↓
Кому к нему действительно нужен доступ?
        ↓
Что можно запретить полностью?
        ↓
Какие разрешённые пути остаются рискованными?
        ↓
Какая телеметрия доступна на этих путях?
        ↓
Какой механизм detection / prevention нужен?
```

Таким образом, IDS/IPS появляется в архитектуре не потому, что «так положено», а потому что остаётся **конкретный риск внутри необходимого взаимодействия**.

## 9. Цена автоматического предотвращения

В первой главе мы уже говорили, что IPS может находиться в позиции, где способна остановить трафик.

Теперь становится понятнее, почему это архитектурно чувствительно.

Если правило межсетевого экрана ошибочно блокирует разрешённый сервис, бизнес сразу ощущает проблему.

Если IPS ошибочно классифицирует легитимный запрос как атаку и автоматически его блокирует, результат для пользователя может быть таким же.

Поэтому при проектировании prevention важно учитывать не только:

> «Можем ли мы это заблокировать?»

но и:

> **«Что произойдёт с сервисом, если решение окажется ошибочным?»**

Позже мы отдельно разберём False Positive, качество детектирования, fail-open/fail-close и отказоустойчивые схемы inline IPS.

## 10. Небольшой архитектурный сценарий

Есть трёхуровневое приложение:

```text
Internet
   ↓
Web
   ↓
Application
   ↓
Database
```

Слабая схема:

```text
Internet → Web        ALLOW
Internet → App        ALLOW
Internet → Database   ALLOW
```

и попытка компенсировать всё множеством IDS-правил.

Более сильный подход начинается с ограничения путей:

```text
Internet → Web         ALLOW 443
Internet → App         DENY
Internet → Database    DENY

Web → App              ALLOW only required service
App → Database         ALLOW only required DB connection
```

А уже на разрешённых путях добавляется необходимая видимость и detection.

В этом случае даже если один детектор что-то пропустил, сетевое разделение продолжает ограничивать возможное движение атакующего.

<div class="chapter-summary">
  <span>Главная мысль главы</span>
  <p>Межсетевой экран и IDS/IPS решают связанные, но разные задачи. Сначала архитектура ограничивает ненужный доступ и уменьшает поверхность атаки. Затем оставшиеся необходимые взаимодействия анализируются на признаки угроз. Современный NGFW может объединять эти функции в одном продукте, но инженер всё равно должен понимать, какое именно решение над трафиком принимается на каждом этапе.</p>
</div>
