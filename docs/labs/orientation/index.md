## Что вы должны понять

После практикума студент должен уметь показать на своей VM:

```text
что установлено
      ↓
каким файлом система настраивается
      ↓
откуда она может получать сетевые данные
      ↓
где находятся подготовленные условия обнаружения
      ↓
куда записываются результаты
```

Это операционная карта системы. Подробная внутренняя архитектура будет разобрана в Главе 3, а устройство правил — в Главе 6.

---

## 1. Убедитесь, что среда готова

Практикум выполняется после [подготовки лабораторной среды](../environment/).

На `idps-server` предыдущая проверка должна завершаться строкой:

```text
SERVER ENVIRONMENT READY
```

Если этого статуса нет, сначала исправьте среду. Практикум не предназначен для обхода ошибок установки или сети.

---

## 2. Что именно установлено

На `idps-server` выполните:

```bash
suricata -V
```

Затем:

```bash
suricata --build-info | sed -n '1,20p'
```

Первая команда показывает фактически установленную версию. Вторая — сведения о сборке и доступных возможностях.

!!! important
    Наличие возможности в `--build-info` означает только, что данная сборка в принципе её поддерживает. Это ещё не доказывает, что функция включена в текущей конфигурации или использовалась в конкретном эксперименте.

---

## 3. Найдите основной файл конфигурации

```bash
ls -l /etc/suricata/suricata.yaml
```

Основной конфигурационный файл курса:

```text
/etc/suricata/suricata.yaml
```

Пока не редактируйте его. На этом этапе нужно понять только роль файла: он описывает настройки движка, источники и режимы обработки, вывод результатов и другие параметры.

Проверьте, что базовая конфигурация разбирается:

```bash
EMPTY_RULES=$(mktemp)
sudo suricata -T \
  -c /etc/suricata/suricata.yaml \
  -S "$EMPTY_RULES"
rm -f "$EMPTY_RULES"
```

Успешный `-T` означает: конфигурация синтаксически пригодна для запуска в данном окружении. Он не означает, что трафик уже наблюдается и что обнаружение работает.

---

## 4. Почему системная служба Suricata остановлена

Проверьте состояние:

```bash
systemctl is-active suricata || true
```

В стенде курса нормальным состоянием перед лабораторией является:

```text
inactive
```

Это сделано намеренно. В лабораторных Suricata запускается вручную на **конкретном учебном интерфейсе**, чтобы студент видел связь между точкой получения данных и результатом.

То есть:

```text
установлено ≠ запущено
запущено ≠ получает нужный трафик
получает трафик ≠ обязательно формирует оповещение
```

---

## 5. Найдите интерфейс учебной сети

```bash
ip -br -4 addr
```

Определите интерфейс с адресом `10.13.37.20/24`:

```bash
LAB_IFACE=$(ip -o -4 addr show | awk '$4 ~ /^10\.13\.37\.20\// {print $2; exit}')
echo "$LAB_IFACE"
```

Этот интерфейс будет источником сетевых данных в первых экспериментах.

Важно различать:

- **источник данных** — сетевой трафик;
- **точку получения данных** — конкретный интерфейс;
- **метод обнаружения** — способ решить, является ли наблюдение интересующим;
- **результат** — например, запись об оповещении.

---

## 6. Где находятся условия обнаружения

Стандартная установка может содержать собственный набор правил, но лаборатории курса используют отдельные учебные файлы из bundle каждой работы.

Например, в ЛР №1 файл находится внутри пакета:

```text
server/lab01.rules
```

До Главы 6 студент **не обязан разбирать синтаксис правила**. В ранних работах правило предоставлено как готовое машинно-исполняемое условие. Вы будете проверять причинно-следственную связь между наблюдаемым запросом и результатом, а не учиться писать правила раньше времени.

---

## 7. Где появляется результат

Suricata может записывать структурированные события в EVE JSON. В лабораториях мы будем явно задавать отдельный каталог вывода через параметр `-l`, например:

```text
~/lab01-output/eve.json
```

Проверять записи удобно утилитой `jq`.

Важно:

```text
EVE JSON — представление результатов и телеметрии;
это не «графический интерфейс IDS» и не сама IDS.
```

---

## 8. А где графический интерфейс?

У Suricata нет единственного обязательного GUI, который можно считать «интерфейсом любой IDS/IPS». Сам движок может работать как системный процесс и писать структурированные результаты. Эти результаты затем могут отображаться в Kibana, EveBox, SIEM, специализированной консоли производителя или другой системе визуализации.

В этом курсе сначала используется более прозрачная цепочка:

```text
Suricata
   ↓
структурированный результат eve.json
   ↓
jq / журнал
```

Так студент видит происхождение данных. Позже графическая визуализация может использоваться как дополнительный слой представления, но она не подменяет понимание самого движка.

## 9. Минимальная операционная карта

Перед переходом к ЛР №1 студент должен без подсказки ответить:

1. Какая версия Suricata установлена?
2. Где находится основной конфигурационный файл?
3. Почему системная служба Suricata перед лабораторией остановлена?
4. Как определить интерфейс `IDPS-LAB`?
5. Где лаборатория хранит подготовленное условие обнаружения?
6. Где появится структурированный результат?
7. Почему наличие `eve.json` ещё не доказывает наличие атаки?

Если эти ответы понятны, первая лабораторная уже не начинается с неизвестного инструмента.
