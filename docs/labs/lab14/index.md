# Лабораторная работа №14 — Можно ли доверять результату анализа?

<div class="chapter-lead">
<p>В №13 вы связали клиентские записи, HTTP-события и alerts. Теперь проверим границы этого анализа: <strong>что произойдёт, если часть данных исчезнет, записи продублируются или время станет противоречивым?</strong> Вы научитесь различать неполные данные, изменение результата обнаружения и ограничения самой проверки.</p>

## 1. Исследовательский вопрос

Исходное утверждение для проверки:

> «Скрипт завершился успешно — значит данные полны, часы точны и инцидента нет».

Это три разных утверждения. Программа проверяет только заложенные в неё условия. Корректное сопоставление записей не удостоверяет происхождение файлов, не устанавливает полноту наблюдения и не заменяет решение аналитика.

**Негативный тест** — проверка ожидаемого поведения на заведомо неподходящих данных. **Ожидаемый результат теста** задаётся до запуска, исходя из известного изменения. Если вход повреждён и программа явно отказалась делать вывод, такой тест пройден. Если программа аварийно завершилась из-за ошибки своего кода, это другой результат.

Здесь проверяется утилита сопоставления из №13, а не устойчивость Suricata к повреждённому PCAP. Мы не повторяем измерение точности правила из №12: пропуск журнала нельзя автоматически посчитать TN, FN или доказательством отсутствия атаки.

## 2. Сохраните связь с исходными материалами

Нужна завершённая попытка №13 на сервере:

| Путь внутри каталога №13 | Назначение |
|---|---|
| `evidence/client-copy/` | Девять файлов A/B/C: запрос, ответ, метаданные |
| `evidence/analysis/eve.json` | Результат исходного offline-разбора |
| `evidence/analysis/active.rules` | Правило, сохранённое при разборе |
| `evidence/analysis/completed.txt` | Отметка завершения анализа |
| `evidence/capture/requests.pcap` | Исходный сетевой захват |

Повторите проверку клиентского `SHA256SUMS` и серверного манифеста из №13, если они были сохранены. Для штатного расположения:

```bash
cd ~/idps-lab13-bundle-v0.1
(cd evidence/client-copy && sha256sum -c SHA256SUMS)
sudo sha256sum -c server-evidence.sha256
```

Если манифест отсутствует, укажите это ограничение: новый хеш не восстанавливает историю файла. При несовпадении сохранённых хешей сначала разберите причину; не заменяйте старый манифест новым ради успешной проверки.

Подготовка №14 дополнительно проверяет исходное сопоставление и ожидаемую картину A=0, B=1, C=1. Это условие воспроизводимости данного опыта, а не универсальная норма для расследований. Если №13 вернула иной результат, сохраните его и разберите по №13. Не дорисовывайте события для прохождения проверки.

## 3. Распакуйте пакет на сервере

Сохраните ZIP и checksum рядом:

```bash
cd ~
sha256sum -c idps-lab14-bundle-v0.1.zip.sha256
unzip -l idps-lab14-bundle-v0.1.zip
test ! -e idps-lab14-bundle-v0.1 && unzip idps-lab14-bundle-v0.1.zip
cd idps-lab14-bundle-v0.1
```

Продолжайте только при успешной проверке и распаковке. Для повторной попытки используйте новый родительский каталог, например `unzip idps-lab14-bundle-v0.1.zip -d lab14-attempt-02`. Не распаковывайте поверх прежних результатов.

```bash
sudo python3 tools/prepare-cases.py ~/idps-lab13-bundle-v0.1
```

Если №13 лежит в другом месте, передайте её фактический каталог. Нужен именно каталог пакета, внутри которого находится `evidence`.

Скрипт сохраняет SHA-256 исходных файлов, небольшую побайтовую копию входов и девять отдельных вариантов. PCAP остаётся в исходном каталоге, его путь и хеш записываются в `evidence/sources.json`. Проверка хешей повторяется после копирования. Каталог `evidence` создаётся только один раз: при ошибке частичные материалы остаются для диагностики, повтор выполняется в новой распаковке.

Каждый вариант содержит `derivation.json`: описание преобразования, ожидаемый код и хеши производных файлов. Пометка `DERIVED_TEST_INPUT_NOT_SENSOR_ORIGINAL` означает **учебные производные данные**. Изменённый EVE не является реальным выводом сенсора и не доказывает, что такая ситуация произошла в сети.

Манифесты помогают заметить случайное изменение. Они не являются цифровой подписью: одновременная подмена файла и его хеша не будет ими выявлена. Доступ к оригиналам и независимая история получения по-прежнему важны.

## 4. Сначала запишите прогноз

До запуска проверок заполните прогноз и объяснение в `report/lab14-report.md`. Для каждого сценария ответьте: можно ли связать записи; какой вывод нужно ограничить; какие данные потребуются дополнительно?

| Сценарий | Изменение относительно эталонной копии |
|---|---|
| `00-reference` | Байты входов сохранены без изменений |
| `01-missing-http` | Удалена HTTP-запись B, её alert сохранён |
| `02-duplicate-alert` | Добавлена вторая копия alert B |
| `03-wrong-client-port` | Изменён локальный порт в метаданных клиента B |
| `04-missing-response` | Удалён файл ответа клиента B |
| `05-shuffled` | Строки EVE расположены в обратном порядке, значения сохранены |
| `06-clock-shift` | Все временные отметки EVE сдвинуты на +300 секунд; клиентские не менялись |
| `07-no-alert` | Удалены все alerts SID 10000130, HTTP-записи сохранены |
| `08-broken-json` | Добавлена строка с незавершённым JSON |

В обычном расследовании причина расхождения заранее неизвестна. Здесь она известна, потому что мы сами задали преобразование. Не переносите это знание на реальные журналы: дубликат может возникнуть при доставке, а пропуск — при фильтрации, ротации или сборе; конкретную причину ещё нужно установить.

## 5. Проверьте эталон и один неполный вариант вручную

Из каталога №14:

```bash
sudo python3 tools/correlate.py evidence/cases/00-reference/client evidence/cases/00-reference/eve.json
printf 'Код завершения: %s\n' "$?"
sudo python3 tools/correlate.py evidence/cases/01-missing-http/client evidence/cases/01-missing-http/eve.json
printf 'Код завершения: %s\n' "$?"
```

`$?` читается сразу после команды, иначе он будет относиться к другой операции. У эталона ожидается код 0, у неполного варианта — 1 и явное сообщение `INCOMPLETE_OR_INVALID`. Отказ сопоставить неполные данные здесь ожидаем.

Откройте исходный и производный EVE, найдите request ID B. Сопоставьте наличие HTTP и alert. Используйте номера строк только вместе с именем файла: после удаления или перестановки строк номера меняются.

## 6. Выполните все проверки

```bash
sudo python3 tools/run-checks.py
```

Скрипт проверяет хеши источников и производных входов, запускает анализатор для каждого сценария и сохраняет фактические stdout, stderr и код завершения в `evidence/results/`. Сводка — `summary.json`. Повторная запись поверх этой папки запрещена.

| Код анализатора | Значение | Сценарии с ожидаемым результатом |
|---|---|---|
| 0 | Связи построены, количество alerts соответствует прогнозу №13 | reference, shuffled, clock-shift |
| 1 + `INCOMPLETE_OR_INVALID` | Недостаточные, неоднозначные или некорректные входы | missing-http, duplicate-alert, wrong-client-port, missing-response, broken-json |
| 2 + `OBSERVED_DIFFERENCE` | Записи связаны, картина alerts отличается от прогноза | no-alert |

`PASS` в сводке означает совпадение **поведения анализатора** с ожидаемым результатом теста. Это не заключение об инциденте, не доказательство точности времени и не оценка качества IDS. Сам `run-checks.py` возвращает 0, если все девять контрактов выполнены; коды отдельных запусков сохраняются отдельно.

Если получили `FAIL`, изучите stdout/stderr соответствующего сценария. Не меняйте ожидаемые значения для получения зелёной сводки. Ошибка Python, отсутствие интерпретатора или отказ доступа не должны выдаваться за успешный негативный тест. Сообщение `CHECK_FAILED` до запуска сценариев означает проблему подготовки или сохранности входов.

## 7. Разберите два успешных, но ограниченных результата

### Перестановка строк

В `05-shuffled` значения событий сохранены, но номера строк изменились. Связь по идентификаторам и соединению сохраняется. Значит, номер строки полезен как ссылка на конкретный файл, но не является универсальной временной шкалой.

Сравните request ID, `flow_id`, `tx_id`, порт и timestamps у B в выводах reference и shuffled. Объясните, почему выбор «предыдущей строки» или ближайшего по положению alert был бы ненадёжен.

### Сдвиг времени

В `06-clock-shift` анализатор возвращает 0: он проверяет наличие часового пояса и внутренний порядок клиентских отметок, но не согласованность часов клиента и EVE. Это известная граница его контракта. Сдвиг в копии не означает изменение системных часов или реальную задержку сети.

Сравните время HTTP B в reference и clock-shift: разность должна составлять ровно 300 секунд. Клиентские отметки остаются прежними. **Это величина внесённого нами изменения**, а не измерение исходного расхождения часов.

В отчёте предложите отдельную проверку временной согласованности: какие часы сравнивать, откуда получить допустимую погрешность, что делать при неизвестной поправке. Не задавайте универсальный порог «пять секунд» без основания. Если неопределённость неизвестна, нельзя превращать разность часов в сетевую задержку.

## 8. Отсутствие alert и решение аналитика

В `07-no-alert` HTTP-записи и клиентские обмены сохранены, а целевые alerts удалены. Анализатор может связать обмены и сообщает отличие от прогноза. Он не должен автоматически объявлять отсутствие сетевого обращения или отсутствие инцидента.

Известная причина в этом опыте — наше преобразование. В реальной ситуации проверялись бы активное правило, параметры разбора, полнота источника и маршрут доставки журнала. Для проверки происхождения EVE полезны PCAP и параметры повторного offline-разбора. EVE, повторно полученный из того же PCAP, не становится независимым наблюдением сети.

Для четырёх случаев — missing-http, wrong-client-port, clock-shift и no-alert — составьте короткую запись передачи следующему аналитику:

1. Что установлено с указанием файла и идентификатора.
2. Что нельзя заключить по доступным данным.
3. Какую следующую проверку выполнить и какой результат изменит решение.

Пример формы: «В предоставленном варианте … отсутствует …; это ограничивает …; требуется проверить …». Не подменяйте отсутствие свидетельства утверждением об отсутствии события. Для структурно повреждённого набора сначала восстанавливают пригодность данных; для связанного набора с иной картиной alerts исследуют причину различия.

## 9. Завершение и отчёт

```bash
sudo python3 tools/prepare-cases.py --verify
sudo find evidence -type f -print0 | sort -z | sudo xargs -0 sha256sum > lab14-evidence.sha256
```

Ожидается `SOURCES_UNCHANGED`. Это сравнение с хешами, записанными в начале №14; оно не удостоверяет более раннюю историю оригиналов. Сохраните исходную попытку №13 по записанному пути до завершения проверки работы.

Сдайте заполненный `report/lab14-report.md`, папку `evidence`, манифест `lab14-evidence.sha256` и доступный комплект исходных артефактов №13. PCAP не размножается по девяти вариантам. Если передаёте комплект на другой компьютер, укажите новое расположение оригиналов; абсолютный путь в манифесте описывает место выполнения опыта.

В отчёте должны быть прогнозы, фактические коды, ссылки на диагностические строки, сравнение времени и четыре записи передачи. Девять `PASS` без объяснения ограничений не заменяют аналитическую часть. Новая балльная шкала не вводится. Останавливать службы или откатывать firewall после №14 не требуется: работа не изменяла их.
