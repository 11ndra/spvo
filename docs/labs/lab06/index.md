# Лабораторная работа №6 — Эксплуатация уязвимостей приложений

**Цель:** на учебном приложении подтвердить SQL-инъекцию, Reflected XSS, командную инъекцию и включение локального файла; для каждой указать механизм, наблюдаемый эффект и защиту. Тема и обязательные виды уязвимостей соответствуют ЛР №6 УМКД (с. 57–58). Здесь выполняется настоящая эксплуатация DVWA, а не отправка условных маркеров детектору.

Контрольная сумма подтверждает совпадение байтов, но не заменяет независимую подпись. Копия пакета на клиенте нужна для отчёта. На сервере распаковывайте в `~/idps-lab06-09-bundle-v1.0`, чтобы последующие команды совпадали с инструкцией.

## Среда и границы опыта

Остаются `idps-client` (Ubuntu Desktop, `10.13.37.10`) и `idps-server` (Ubuntu Server, `10.13.37.20`). Добавляется **DVWA на TCP/4280** в отдельном Docker Compose проекте. Сервис ЛР №5 на `8080` не заменяется. Третья VM, Kali и переустановка ОС не нужны: инструменты запускаются на существующем Ubuntu. Это замена платформы из примера УМКД при сохранении практических заданий.

**Разрешённая цель:** только `http://10.13.37.20:4280` своего стенда. Браузер и Burp запускайте на `idps-client`. Используйте встроенные вымышленные записи DVWA. Не загружайте свои документы, не используйте реальные пароли. Командная инъекция ограничена `whoami`, чтение файла — `/etc/passwd` внутри учебного контейнера. Этот файл содержит сведения об учётных записях, а не их парольные хеши.

Сеть VirtualBox — прежняя Host-Only + NAT, без Bridged и без переадресации портов на роутере. Не выставляйте DVWA в Интернет. Compose привязывает веб-порт к `10.13.37.20`, не публикует БД и использует отдельную bridge-сеть проекта. Такая привязка ограничивает входящие подключения, но сама по себе не запрещает исходящие соединения. Docker меняет правила сети хоста; обычный запрет UFW сам по себе не доказывает закрытость опубликованного контейнерного порта.

## Подготовка до занятия

**Преподаватель готовит стенд заранее.** Установка и скачивание образов не входят в аудиторные 60 минут. На сервере нужны Docker Engine и Compose plugin по [официальной инструкции для Ubuntu](https://docs.docker.com/engine/install/ubuntu/), а также `git`, `curl`, `python3`. На клиенте — [Burp Suite Community](https://portswigger.net/burp/documentation/desktop/getting-started/download-and-install), его встроенный браузер и SQLmap. Для штатного клиента Ubuntu 24.04 SQLmap можно подготовить командой `sudo apt install sqlmap`; проверьте `sqlmap --version`. Сохраните версии инструментов. Для Burp предусмотрите не менее 4 ГБ RAM на клиенте; при нехватке памяти подготовьте рабочее место до урока.

На сервере из каталога пакета:

```bash
bash setup/prepare.sh
sudo docker compose -f setup/compose.yaml config
sudo docker compose -f setup/compose.yaml build dvwa
sudo docker compose -f setup/compose.yaml up -d
sudo docker compose -f setup/compose.yaml ps
bash setup/record.sh
curl --noproxy '*' -I --max-time 10 http://10.13.37.20:4280/login.php
```

`prepare.sh` скачивает официальные исходники DVWA и закрепляет commit `a1978a2fed195acd093010af6395f86a281537ca`; существующий каталог не перезаписывает. Приложение собирается из этих исходников. Образ БД и базовые образы сборки используют теги: **один commit не обеспечивает побитовую воспроизводимость всего окружения**. `record.sh` сохраняет image IDs, версии Docker/Compose, конфигурацию и хеши исходников в новом каталоге `evidence/environment-*`. Для группы используйте один проверенный снимок подготовленной VM. Повторная сборка для ЛР №7 не нужна.

Убедитесь, что `db` имеет состояние healthy, `dvwa` запущен, а единственный опубликованный порт проекта — `10.13.37.20:4280`. HTTP 200 или перенаправление ещё не подтверждает готовность базы. В браузере клиента откройте `/setup.php`, нажмите **Create / Reset Database** только для выделенной DVWA, затем войдите на `/login.php` с учебными `admin` / `password`. Не сбрасывайте БД между опытами без сохранения результатов.

Откройте **DVWA Security**, выберите **Low**, нажмите Submit. Проверьте отображаемый уровень. Выполните обычный запрос SQL Injection с ID `1`: должна появиться одна запись. Это проверка готовности. Если возникает ошибка БД, смотрите `sudo docker compose -f setup/compose.yaml logs db dvwa`; не считайте ошибку приложения успешной атакой.

После скачивания всех зависимостей и проверки приложения на время опытов отключите в VirtualBox только **Cable connected / Кабель подключён** у NAT-адаптера обеих VM. Host-Only оставьте подключённым, IP и маршруты вручную не меняйте. Работа DVWA, SQLmap и Burp с локальной целью не требует Интернета. Проверьте доступ к DVWA с клиента после отключения; восстановите NAT после остановки проекта по завершении ЛР №7.

В Burp откройте **Proxy → Open browser**, перейдите в DVWA, добавьте только этот адрес и порт в scope. В HTTP history включите отображение in-scope. Основную работу выполняйте с **Intercept off**; перехват включайте только на нужный запрос. Приложение не должно «зависать» из-за оставленного перехвата. Сохраняйте запрос и ответ через меню редактора сообщения, а не только снимок списка запросов.

## Что считается доказательством

| Наблюдение | Допустимый вывод | Чего оно не доказывает |
|---|---|---|
| Изменился набор записей SQL | Ввод изменил результат запроса | Полный доступ ко всей БД |
| Выполнился `alert` в браузере | Выполнение JavaScript в этом контексте | Кражу cookie или захват аккаунта |
| В HTTP-ответе появился результат `whoami` | Выполнение команды в контейнере | Выполнение от root на VM |
| Получен `/etc/passwd` | Чтение конкретного локального файла | Доступ к `/etc/shadow` или хостовой ФС |

Для каждого опыта сначала сохраните нормальный запрос, затем меняйте один параметр. Запишите время, уровень DVWA, метод/путь, параметр, ожидаемый и фактический эффект. В отчёте используйте `report/lab06-report.md`.

## 1. SQL-инъекция

В **SQL Injection**, уровень Low:

1. Отправьте ID `1`; сохраните запрос, ответ и число записей.
2. В поле ID введите `' OR '1'='1` и отправьте форму. Это часть выражения для строкового контекста конкретного учебного запроса.
3. Сравните число и содержимое возвращённых учебных записей. Подтверждение — несколько разных пользователей вместо одной записи, а не просто HTTP 200.
4. Откройте **View Source**. Найдите конкатенацию ввода с SQL. Объясните, почему параметризованный запрос отделяет данные от SQL-синтаксиса.

На клиенте заранее создайте каталог `evidence` командой `mkdir -p evidence`. В Burp сохраните **исходный нормальный запрос с ID `1`** в `evidence/sqli-baseline.req` на клиенте. Он должен содержать актуальный Cookie учебной сессии и адрес `10.13.37.20:4280`. Убедитесь, что запрос не относится к странице login. Для узкой проверки автоматизированным инструментом:

```bash
mkdir -p evidence
sqlmap -r evidence/sqli-baseline.req -p id --batch \
  --level=1 --risk=1 --technique=B --threads=1 \
  --timeout=5 --retries=0 --current-db --output-dir=evidence/sqlmap
```

SQLmap ограничен одним параметром и boolean-based проверками; дамп БД и OS shell не нужны. Сохраните вывод. Если инструмент не подтвердил инъекцию, проверьте сессию/Low и сопоставьте с ручным результатом: один неудачный запуск не опровергает показанную уязвимость. Эксплуатацию оценивайте по эффекту, вывод инструмента — отдельный источник.

## 2. Reflected XSS

В **XSS (Reflected)**, Low:

1. Отправьте `student06` и сохраните обычный ответ.
2. Отправьте `<script>alert('LAB06-XSS')</script>`.
3. Зафиксируйте всплывающее окно и соответствующий ответ. Откройте страницу без параметра: эффект не должен самопроизвольно сохраняться.
4. Через View Source найдите вывод входного значения без HTML-кодирования. Опишите защиту для HTML-контекста и отличие от Stored XSS.

Наличие строки `<script>` в ответе само по себе не доказывает исполнение. Если окна нет, фиксируйте фактический результат, проверьте уровень, браузерную консоль и ответ; не отключайте защиту основного браузера. Используйте отдельный учебный браузер Burp.

## 3. Command Injection

В **Command Injection**, Low:

1. Отправьте `127.0.0.1`; дождитесь окончания ping и сохраните ответ.
2. Отправьте `127.0.0.1; whoami`.
3. Выделите в ответе строку имени пользователя, отличную от вывода ping. Сопоставьте с `shell_exec` в исходнике.
4. Объясните, почему отказ от shell и строгая проверка аргументов надёжнее удаления нескольких запрещённых символов.

Не запускайте установку ПО, reverse shell, изменение файлов или команды хоста. Ввод проходит в shell **контейнера DVWA**; `127.0.0.1` здесь — его loopback.

## 4. Local File Inclusion и Path Traversal

Откройте **File Inclusion**. Сначала штатный `?page=file1.php`, затем только в своём DVWA:

```text
http://10.13.37.20:4280/vulnerabilities/fi/?page=/etc/passwd
http://10.13.37.20:4280/vulnerabilities/fi/?page=../../../../../../etc/passwd
```

Сохраните оба запроса и фрагмент результата без лишних данных. Успех подтверждается содержимым файла, а не сообщением об ошибке. Абсолютный путь демонстрирует отсутствие разрешённого списка включаемых файлов; относительный путь дополнительно показывает traversal. В DVWA используется `include`: включение и чтение файла здесь связаны, но не тождественны любому произвольному скачиванию файла в веб-приложении.

Предложите отображение безопасного идентификатора в заранее разрешённый файл; объясните, почему блокировка только `../` неполна. В ЛР №7 сравним это с уровнями защиты.

## Отчёт и завершение

План 60 минут на готовом стенде: 5 — проверка среды; 15 — SQLi и SQLmap; 10 — XSS; 10 — команды; 10 — файлы; 10 — выводы. Если установка или сбой съели занятие, зафиксируйте невыполненные опыты, а не заполняйте ожидаемые ответы как наблюдения.

Сдайте четыре карточки уязвимостей: **обычный запрос → изменённый запрос → наблюдаемый эффект → причина в исходнике → защита**. Приложите вывод SQLmap, версии среды, собственные снимки и существенные части HTTP. В копии для сдачи удалите Cookie/Set-Cookie, токены и идентификаторы сессий. Исходники HTTP с учебной сессией храните локально, на Pages их не загружайте. Если результат не воспроизвёлся, приложите диагностические данные и обозначьте пробел.

По окончании остановите контейнеры, сохранив БД для следующей работы:

```bash
sudo docker compose -f setup/compose.yaml stop
```
