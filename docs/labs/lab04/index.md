# Лабораторная работа №4

## Один набор событий — четыре метода обнаружения

<div class="lab-header">
<strong>Цель:</strong> экспериментально разделить сигнатурное обнаружение, анализ состояния/семантики, поведенческий анализ и аномальное обнаружение, не меняя источник данных между экспериментами.
</div>

<div class="chapter-lead">
<p>В этой работе мы специально <strong>не пишем собственные Suricata rules</strong>. Это будет темой следующей главы. Здесь важнее увидеть, что один и тот же набор событий может анализироваться по разным основаниям, а результат каждого детектора поддерживает разные выводы.</p>
</div>
!!! info "Статус проверки лабораторной"
    - `DESIGN VERIFIED` — источник данных и набор событий фиксированы, а изменяется только принцип анализа; допустимые выводы для четырёх методов разделены.
    - `STATIC QA PASSED` — проверены пути, bundle `v0.1`, shell/Python syntax и детерминированная simulation на 19 событиях.
    - `RUNTIME QA REQUIRED` — полный сценарий `setup → preflight → client check → reset → scenario → analysis` на двух эталонных Ubuntu VM ещё не получил статус `RUNTIME VERIFIED`.

## 1. Что именно мы меняем в эксперименте

## 4. Выполните один контролируемый сценарий

На `idps-client`:

```bash
bash client/run-scenario.sh
```

Сценарий создаёт четыре части:

```text
1. baseline:
   6 запросов /catalog с интервалом около 0.8 с;

2. known marker:
   1 запрос /download/LAB4-KNOWN-BAD;

3. state-machine:
   DATA до START, затем корректные START → DATA → END;

4. burst:
   после технической паузы 2.2 с — 8 запросов /catalog без искусственной задержки.
```

Пауза перед burst нужна только для чистоты эксперимента: она гарантирует, что двухсекундное окно поведенческого детектора не содержит хвост baseline. Внутри burst задержка не добавляется.

Ожидаемое завершение:

```text
SCENARIO COMPLETE. Ожидается 19 событий в чистом журнале.
```

На сервере:

```bash
wc -l /var/tmp/idps-lab/lab4-events.jsonl
```

Ожидается `19` строк.

Если число другое, не продолжайте интерпретацию. Сначала выясните, был ли журнал действительно очищен и завершился ли сценарий полностью.

## 5. Сначала посмотрите на исходные события

На сервере:

```bash
sed -n '1,25p' /var/tmp/idps-lab/lab4-events.jsonl
```

Не пытайтесь пока решить, какие события «опасные». Ваша задача — подтвердить, что детекторы дальше получают **один и тот же исходный набор данных**.

Проверьте порядок session-событий:

```bash
grep '"path": "/session/' /var/tmp/idps-lab/lab4-events.jsonl
```

Вы должны увидеть:

```text
/session/data
/session/start
/session/data
/session/end
```

Первое `DATA` намеренно идёт раньше `START`.

# Часть A. Сигнатурный метод

## 6. Примените детектор известного признака

```bash
python3 server/analyze-methods.py --method signature
```

Ключевой ожидаемый результат:

```text
METHOD=signature
CONDITION=path == /download/LAB4-KNOWN-BAD
MATCHES=1
SIGNATURE MATCH ...
```

Детектор не анализирует частоту, baseline или состояние session-протокола. Он отвечает на один вопрос:

> присутствует ли заранее определённый признак?

<div class="lab-evidence">
<strong>Допустимый вывод</strong>
<p>В журнале присутствует событие, которое совпало с заранее определённым условием сигнатурного детектора.</p>
</div>

Нельзя делать вывод:

```text
совпадение маркера → доказана компрометация
```

`LAB4-KNOWN-BAD` — синтетический учебный маркер.

# Часть B. Состояние и семантика

## 7. Примените state-machine detector

```bash
python3 server/analyze-methods.py --method protocol
```

Используется учебная модель:

```text
IDLE --START--> OPEN
OPEN --DATA--> OPEN
OPEN --END--> IDLE
```

Ключевой ожидаемый результат:

```text
METHOD=protocol
VIOLATIONS=1
STATE VIOLATION ... state=IDLE action=DATA
```

Первое `DATA` синтаксически является обычным HTTP-запросом, но нарушает **состояние синтетического прикладного протокола**, заданного для лаборатории.

!!! important
    `START → DATA → END` не является правилом стандарта HTTP. Это специально созданный учебный протокол поверх HTTP-маршрутов, позволяющий сделать состояние явным и воспроизводимым.

<div class="lab-evidence">
<strong>Допустимый вывод</strong>
<p>Наблюдаемая последовательность нарушила заданную state-machine учебного протокола.</p>
</div>

Нельзя делать вывод:

```text
state violation → HTTP-атака доказана
```

# Часть C. Поведенческий метод

## 8. Примените фиксированный временной порог

```bash
python3 server/analyze-methods.py --method behavior
```

Детектор использует условие:

```text
один источник
+ /catalog
+ не менее 5 запросов
+ в пределах 2 секунд
```

Ключевой ожидаемый результат:

```text
METHOD=behavior
CONDITION=>=5 /catalog requests from one source within 2.0s
MATCHES=1
BEHAVIOR MATCH ...
```

Обратите внимание: baseline для принятия решения не использовался.

Порог `5 за 2 секунды` был определён **до анализа**.

<div class="lab-evidence">
<strong>Допустимый вывод</strong>
<p>В контролируемом наборе событий выполнено заранее заданное поведенческое условие.</p>
</div>

Нельзя утверждать:

```text
behavior match → активность доказанно аномальна для реальной организации
```

Для этого пока нет модели реальной нормы.

# Часть D. Аномальное обнаружение

## 9. Сравните burst с baseline

Теперь используется тот же `/catalog`, но принцип решения другой.

```bash
python3 server/analyze-methods.py --method anomaly
```

Детектор берёт события с меткой `baseline`, вычисляет медианный интервал между ними и сравнивает его с burst.

Ожидаемая форма результата:

```text
METHOD=anomaly
BASELINE_EVENTS=6 BURST_EVENTS=8
BASELINE_MEDIAN_INTERVAL=...
BURST_MEDIAN_INTERVAL=...
SPEED_RATIO=... THRESHOLD=3.00x
ANOMALY=YES
```

Точные значения интервалов зависят от скорости VM. Важен принцип: burst должен быть как минимум в три раза быстрее baseline по медианному интервалу.

Если `ANOMALY=NO`, повторите эксперимент после очистки журнала и убедитесь, что baseline действительно создавался с задержкой, а burst — без неё.

<div class="lab-evidence">
<strong>Допустимый вывод</strong>
<p>В данном контролируемом прогоне временная структура burst существенно отклонилась от измеренного baseline по выбранному критерию.</p>
</div>

Нельзя делать вывод:

```text
ANOMALY=YES → malicious=yes
```

И нельзя утверждать, что шесть учебных запросов являются репрезентативной production-моделью. Это только лабораторная базовая линия для демонстрации принципа.

## 10. Сопоставьте все методы

```bash
python3 server/analyze-methods.py --method all
```

В конце должен появиться сводный блок:

```text
=== SUMMARY ===
SIGNATURE=DETECTED
PROTOCOL=DETECTED
BEHAVIOR=DETECTED
ANOMALY=DETECTED
```

Все четыре результата получены из **одного файла событий**, но основания решений различаются.

| Метод | Основание решения | Нужна история нескольких событий? | Нужен baseline? |
|---|---|---:|---:|
| Сигнатурный | заранее известный признак | не обязательно | нет |
| Состояние/семантика | допустимое состояние и переход | да, если состояние зависит от истории | нет |
| Поведенческий | заранее заданное условие над серией | обычно да | не обязательно |
| Аномальный | отклонение от ожидаемой модели | часто да | да, в этой лабораторной |

Главный экспериментальный вывод:

<div class="principle-box">
<strong>BEHAVIORAL ≠ ANOMALY</strong>
<p>Оба детектора анализировали частоту `/catalog`, но поведенческий применял фиксированный порог, а аномальный сравнивал burst с измеренным baseline.</p>
</div>

Студент должен уметь без запуска команд объяснить:

1. Почему источник данных во всех четырёх тестах один и тот же?
2. Что именно делает первый detector сигнатурным?
3. Почему `DATA` до `START` — пример анализа состояния, а не просто совпадение строки?

6. Почему ни один из четырёх результатов сам по себе не доказывает компрометацию?

## Если результат отличается от ожидаемого

| Симптом | Что проверить |
|---|---|
| В журнале больше 19 строк | Был ли выполнен `sudo bash server/reset-evidence.sh` после client check |
| В журнале меньше 19 строк | Завершился ли `run-scenario.sh`; доступен ли `10.13.37.20:8080` |
| `MATCHES=0` для signature | Есть ли строка `/download/LAB4-KNOWN-BAD` в JSONL |
| `VIOLATIONS=0` | Идёт ли первое `/session/data` раньше `/session/start` |
| `MATCHES=0` для behavior | Выполнялся ли burst без искусственной задержки |
| `ANOMALY=NO` | Сравните интервалы baseline/burst; повторите чистый эксперимент на ненагруженных VM |
| `ANOMALY=INDETERMINATE` | Достаточно ли минимум двух событий в обеих фазах |

!!! note "О статусе воспроизводимости"
    Скрипты и логика лаборатории статически проверены, но статус полного end-to-end прохождения на эталонных Ubuntu Desktop/Server 24.04.x остаётся `RUNTIME QA REQUIRED` до фактического прогона на учебных VM.

## Связь с теорией

ЛР №4 изолирует одну переменную — **метод обнаружения**.

```text
одна среда
+ один сервис
+ один журнал событий
+ один контролируемый сценарий
        ↓
четыре разных основания решения
```

Это напрямую закрепляет Главу 5 и подготавливает Главу 6: после того как студент понимает, **какой принцип** хочет реализовать, можно переходить к вопросу, **как выразить условие в правиле конкретного движка**.
