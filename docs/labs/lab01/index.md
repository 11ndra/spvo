### Как читать указания «где выполнять»

В лаборатории одновременно используются две VM и несколько окон. Чтобы не приходилось догадываться, каждый практический блок ниже явно указывает место выполнения:

- **`idps-server` · SSH-сессия 1** — длительные процессы: сначала `tcpdump`, затем Suricata в live-режиме;
- **`idps-server` · SSH-сессия 2** — проверки, `suricata -T`, просмотр `eve.json` и команды `jq`;
- **`idps-client` · терминал** — проверка клиентской стороны и один ручной HTTP-запрос при проверке `tcpdump`;
- **`idps-client` · браузер** — Live Console и четыре эксперимента.

Если следующий шаг выполняется на другой VM или в другом окне, инструкция прямо говорит об этом.

## 1. Подготовьте сценарий ЛР №1

Пакет нужен на обеих VM, потому что в нём есть серверные скрипты и клиентская проверка.

**Где выполнять: `idps-server` · SSH-сессия 2.**

```bash
cd ~
unzip idps-lab01-bundle-v0.8.1.zip
cd idps-lab01-bundle-v0.8.1
sudo bash server/setup-server.sh
sudo bash server/preflight-server.sh
```

Продолжайте только после:

```text
[ OK ] lab target is available on 10.13.37.20:8080
[ OK ] visual console is available on 10.13.37.20:9090
SERVER PRE-FLIGHT PASSED.
```

После успешного server preflight переключитесь на клиент.

**Где выполнять: `idps-client` · терминал.**

```bash
cd ~
unzip idps-lab01-bundle-v0.8.1.zip

bash client/check-client.sh

Продолжайте только после:

```text

Поэтому интерфейс помогает увидеть evidence, но источником результата остаётся работающий сенсор и его журнал.

## 2. Найдите точку наблюдения

Сначала нам нужно определить, через какой интерфейс сервер подключён к учебной сети `10.13.37.0/24`.

**Где выполнять: `idps-server` · SSH-сессия 2.**

```bash
ip -br addr
```

Эта команда показывает интерфейсы и назначенные им адреса в компактном виде. Найдите интерфейс с адресом `10.13.37.20/24`.

Чтобы не вводить имя интерфейса вручную в следующих командах, сохраним его в переменную:

```bash
LAB_IFACE=$(ip -o -4 addr show | awk '$4 ~ /^10\.13\.37\.20\// {print $2; exit}')
echo "$LAB_IFACE"
```

В текущем стенде обычно получится:

```text
enp0s8
```

Здесь важно не само имя `enp0s8`. Мы ищем интерфейс, которому принадлежит адрес сервера в учебной сети `10.13.37.0/24`. Именно через эту сеть клиент `10.13.37.10` обращается к серверу `10.13.37.20`, поэтому этот интерфейс является нашей точкой наблюдения для текущего эксперимента.

Практический смысл: если сенсор получает данные не из той точки, отсутствие alert нельзя автоматически объяснять правилом — сначала нужно доказать, что сам поток вообще доступен сенсору.

## 3. Докажите видимость трафика без Suricata

Прежде чем проверять IDS, убедимся, что нужный поток вообще доступен в выбранной точке.

**Где выполнять: `idps-server` · SSH-сессия 1.**

```bash
sudo tcpdump -nn -i "$LAB_IFACE" \
  'host 10.13.37.10 and tcp port 8080'
```

Что означает эта команда:

| Часть | Смысл |
|---|---|
| `tcpdump` | захватывает наблюдаемые сетевые пакеты |
| `-nn` | не преобразует IP-адреса и номера портов в имена |
| `-i "$LAB_IFACE"` | слушает выбранный интерфейс |
| `host 10.13.37.10` | оставляет трафик, связанный с учебным клиентом |
| `tcp port 8080` | оставляет TCP-трафик учебного HTTP-сервиса |

Оставьте `tcpdump` работающим и переключитесь на клиент.

**Где выполнять: `idps-client` · терминал.**

```bash
curl -sS http://10.13.37.20:8080/normal
```

`curl` отправляет HTTP-запрос. В `tcpdump` должен появиться обмен, включая строку вида:

```text
HTTP: GET /normal HTTP/1.1
```

После получения ответа вернитесь в **`idps-server` · SSH-сессию 1**, где работает `tcpdump`, и остановите его через `Ctrl+C`.

<strong>Контрольная точка 2</strong>
<p>Мы доказали наличие и видимость конкретного сетевого потока. Это ещё не доказывает работу Suricata и не доказывает срабатывание правила.</p>
</div>

## 4. Проверьте конфигурацию и правило

До запуска сенсора проверим, может ли Suricata разобрать основной конфигурационный файл и **подготовленное учебное правило из `server/lab01.rules`**. Пока не нужно разбирать его содержимое: на этом шаге нас интересует только техническая готовность движка загрузить этот файл.

**Где выполнять: `idps-server` · SSH-сессия 2.**

```bash
cd ~/idps-lab01-bundle-v0.8.1

sudo suricata -T \
  -c /etc/suricata/suricata.yaml \
  -S server/lab01.rules
```

Здесь:

| Часть | Смысл |
|---|---|
| `-T` | тестирует конфигурацию и завершает работу, не начиная live-захват |
| `-c ...` | указывает основной конфигурационный файл |
| `-S ...` | загружает наш отдельный учебный файл правил |

Ожидается сообщение:

```text
Configuration provided was successfully loaded. Exiting.
```

Правильный вывод этого шага: конфигурация и правило успешно разобраны. Нельзя пока утверждать, что Suricata увидела трафик или сформировала alert.

## 5. Запустите сенсор

Теперь запускаем Suricata в live-режиме. С этого момента она будет получать сетевые данные с выбранного интерфейса, разбирать доступные ей протоколы, применять загруженное учебное правило и записывать события в каталог текущего запуска.

**Где выполнять: `idps-server` · SSH-сессия 1.** Если в этой сессии ещё открыт старый вывод `tcpdump`, убедитесь, что `tcpdump` уже остановлен.

```bash
cd ~/idps-lab01-bundle-v0.8.1

LAB_IFACE=$(ip -o -4 addr show | awk '$4 ~ /^10\.13\.37\.20\// {print $2; exit}')

mkdir -p "$HOME/lab01-output"
rm -f "$HOME/lab01-output"/*

sudo suricata \
  -k none \
  -c /etc/suricata/suricata.yaml \
  -S "$HOME/idps-lab01-bundle-v0.8.1/server/lab01.rules" \
  -i "$LAB_IFACE" \
  -l "$HOME/lab01-output"
```

Что здесь важно:

| Часть | Смысл |
|---|---|
| `-i "$LAB_IFACE"` | захватывать трафик с выбранной точки наблюдения |
| `-l "$HOME/lab01-output"` | сохранять результаты именно этого запуска в отдельный каталог |
| `-k none` | не отбрасывать учебные пакеты из-за особенностей checksum/offloading виртуальной среды |

Ожидается:

```text
Engine started.
```

Оставьте эту SSH-сессию открытой: Suricata работает в foreground и занимает терминал до остановки. Для остальных команд используйте **`idps-server` · SSH-сессию 2**.

!!! note
    В этой лаборатории используется обычный многопоточный режим Suricata: движок создаёт worker-потоки в соответствии с доступными CPU и capture-конфигурацией.

!!! info "Почему в `suricata.yaml` может встречаться `interface: eth0`"
    Интерфейс текущего live-захвата явно задаёт параметр `-i "$LAB_IFACE"`. Если в секции `af-packet` нет отдельного профиля именно для этого имени интерфейса, Suricata использует профиль `interface: default`. Поэтому пример `interface: eth0` в стандартном конфигурационном файле не означает, что текущий запуск слушает `eth0`.

## Что будет происходить «под капотом»

Перед визуальными экспериментами важно понимать цепочку, которую вы сейчас построили. В этой конкретной лаборатории:

```text
idps-client
   │  HTTP GET к 10.13.37.20:8080
   ▼
учебная сеть 10.13.37.0/24
   │
   ▼
enp0s8 на idps-server
   │
   ├─ tcpdump может показать сам сетевой обмен
   │
   └─ Suricata получает трафик с этого интерфейса
          │
          ├─ для распознанной HTTP-транзакции может записать HTTP event в EVE
          │
          └─ учебное правило SID 1000001 проверяет выбранное представление HTTP-данных
                 │
                 └─ если его условие выполнено, появляется alert event

Live Console :9090 читает эти реальные EVE-события и показывает их в более наглядном виде.
```

Зачем различать эти уровни:

- `tcpdump` помогает доказать, что сетевой поток существует в выбранной точке;
- HTTP event помогает подтвердить, что Suricata распознала и записала соответствующую HTTP-транзакцию;
- alert с SID связывает результат с конкретным правилом;
- `action` показывает действие движка в данном режиме.

Именно поэтому в следующих шагах мы будем спрашивать не просто «сработало или нет», а **какой артефакт подтверждает каждый вывод**.

## 7. Проведите четыре эксперимента

Пока **не открывайте `server/lab01.rules`**. Suricata уже загрузила этот файл через параметр `-S`, но условие намеренно скрыто до конца серии.

SID `1000001` — уникальный идентификатор нашего подготовленного учебного правила. Если в EVE появился alert с этим SID, мы можем сказать: **именно это правило сформировало alert для данного запроса**. Если SID не появился, сначала проверяем наличие HTTP event — так мы отделяем «сенсор не видел запрос» от «запрос был виден, но условие правила не выполнилось».

Во всех четырёх опытах меняется только URI. Это контролируемый эксперимент: остальные основные условия остаются одинаковыми.

В Live Console последовательно проведите:

```text
A  /normal
B  /ATTACK-LAB
C  /test/ATTACK-LAB
D  /attack-lab
```

Перед каждым запросом выберите прогноз: ожидаете ли вы SID `1000001`.

После каждого запуска консоль показывает три отдельных факта:

```text
запрос выполнен
      ↓
HTTP event найден в EVE
      ↓
появился или не появился SID 1000001
```

После каждого опыта сначала смотрите на HTTP event, а уже затем на SID.

- HTTP event есть → Suricata распознала и записала соответствующую HTTP-транзакцию;
- HTTP event есть, SID нет → запрос дошёл до сенсора как HTTP-данные, но данное учебное правило не сформировало alert;
- HTTP event и SID есть → запрос наблюдался, а конкретное правило сформировало alert.

Эта последовательность понадобится дальше при анализе событий: она не позволяет путать отсутствие alert с отсутствием трафика.

После четырёх экспериментов заполнится сравнительная таблица.

## 8. Свяжите результаты с конкретным условием правила

После четырёх экспериментов Live Console показывает **две строки из `server/lab01.rules`** — того самого файла, который Suricata загрузила параметром `-S` при запуске. Полное правило пока изучать не требуется: нам нужны только элементы, объясняющие результат этой серии.

```text
http.uri;
content:"ATTACK-LAB";
```

На этом этапе не требуется знать весь синтаксис правил Suricata. Разберите только две идеи.

`http.uri` выбирает нормализованное представление URI, доступное HTTP-инспектору Suricata. Следующее условие работает уже с этим представлением, а не с абстрактным понятием «атака».

`content:"ATTACK-LAB"` проверяет наличие указанной последовательности символов внутри выбранного представления.

Сопоставьте правило с результатами:

```text
/normal           → последовательности ATTACK-LAB нет
/ATTACK-LAB       → последовательность есть
/test/ATTACK-LAB  → последовательность есть внутри более длинного URI
/attack-lab       → регистр отличается
```

В текущем правиле нет `nocase`, поэтому сравнение чувствительно к регистру.

Главная идея этого этапа:

```text
правило не реагирует на абстрактное понятие «атака»;
оно проверяет конкретное условие над доступным представлением данных.
```

# Часть III. Смотрим под капот

## 9. Посмотрите raw EVE без фильтрации

Live Console уже показала результат. Теперь посмотрим, откуда она его получила.

**Где выполнять: `idps-server` · SSH-сессия 2.** Suricata продолжает работать в SSH-сессии 1.

```bash
tail -n 5 "$HOME/lab01-output/eve.json"
```

`tail -n 5` показывает последние пять строк файла. Каждая строка `eve.json` — отдельный JSON-объект события.

Сырой JSON неудобно читать целиком. `jq` нужен не ради самой команды: он позволяет задать точный вопрос к структурированным событиям и получить только поля, которые нужны для проверки гипотезы.

---

## 10. Найдите HTTP-события через jq

Выполните:

```bash
jq -c '
  select(.event_type=="http") |
  {timestamp, src_ip, dest_ip, url: .http.url, status: .http.status}
' "$HOME/lab01-output/eve.json"
```

Разберём команду:

| Часть | Смысл |
|---|---|
| `select(.event_type=="http")` | оставить только HTTP-события |
| `src_ip`, `dest_ip` | показать источник и назначение |
| `.http.url` | показать URI |
| `.http.status` | показать HTTP status |
| `-c` | вывести каждый результат компактно в одну строку |

Сопоставьте результат с таблицей Live Console. Практический смысл этого шага: если в будущем визуальная панель недоступна или нужно проверить её вывод, те же факты можно извлечь непосредственно из источника evidence.

---

## 11. Найдите alert через jq

Теперь оставьте только alert SID `1000001`:

```bash
jq -c '
  select(.event_type=="alert" and .alert.signature_id==1000001) |
  {
    timestamp,
    src_ip,
    dest_ip,
    url: .http.url,
    sid: .alert.signature_id,
    signature: .alert.signature,
    action: .alert.action
  }
' "$HOME/lab01-output/eve.json"
```

Теперь у вас есть прямая связь между визуальными полями и raw evidence. Это позволяет не просто увидеть alert в интерфейсе, а самостоятельно подтвердить, из каких полей события он построен:

```text
Live Console        EVE JSON
Источник        ←→  src_ip
Назначение      ←→  dest_ip
URI             ←→  http.url
SID             ←→  alert.signature_id
Action          ←→  alert.action
```

## 12. Что означает action: allowed

Для положительных экспериментов alert содержит:

```text
action: allowed
```

В этой лаборатории Suricata работает в IDS-режиме. Поэтому значение означает: правило сформировало alert, но данный запрос не был заблокирован этим сценарием.

Не делайте из `allowed` вывод «запрос безопасен». Это поле описывает действие движка в текущем режиме, а не смысловую оценку запроса.

    Если вместо нормального завершения появляются сообщения ядра `soft lockup`, `RCU stall` или VM перестаёт отвечать на десятки секунд, это не штатный результат лаборатории. Не отправляйте повторные `Ctrl+C`: сначала нужно диагностировать состояние виртуальной машины.

После остановки можно посмотреть финальные строки:

```bash
tail -n 20 "$HOME/lab01-output/suricata.log"
```

## 15. Что вы должны понять после ЛР №1

После работы вы должны разделять следующие факты:

```text
tcpdump видит поток
    → трафик доступен в выбранной точке наблюдения

HTTP event есть в EVE
    → Suricata зарегистрировала соответствующую HTTP-транзакцию

SID 1000001 появился
    → условие конкретного учебного правила выполнилось

SID 1000001 не появился, но HTTP event есть
    → запрос наблюдался, однако условие этого правила не выполнилось

action: allowed
    → alert создан без блокирования запроса в данном IDS-сценарии
```

Ни один из этих артефактов сам по себе не доказывает эксплуатацию или компрометацию системы.

Проверяйте цепочку в том же порядке, в котором строилась лаборатория:

```text
1. адреса двух VM
2. HTTP :8080
3. Live Console :9090
4. выбранный LAB_IFACE
5. tcpdump видит тестовый запрос
6. suricata -T проходит успешно
7. Engine started
8. существует ~/lab01-output/eve.json
9. только после этого анализируйте HTTP events и alerts
```
