# Лабораторная работа №7 — Эксплуатация приложений: проверка защиты

**Цель:** повторить контролируемые проверки SQLi, XSS, командной инъекции и Path Traversal при изменении защиты; отличить блокировку одного ввода от устранения причины. Основа — ЛР №7 УМКД (с. 59–60), включая сравнение Low/Medium и Stored XSS.

## Перед началом

На `idps-server`:

```bash
cd ~/idps-lab06-09-bundle-v1.0
sudo docker compose -f setup/compose.yaml up -d
sudo docker compose -f setup/compose.yaml ps
bash setup/record.sh
```

Используйте подготовленные образы без повторной сборки. На время опытов NAT-кабель обеих VM отключён, Host-Only подключён, как в ЛР №6. На клиенте откройте DVWA в учебном браузере Burp. Проверьте сессию и обычный запрос. В **DVWA Security** уровень меняется кнопкой Submit; фиксируйте его **для каждого опыта**. После перехода на Impossible сначала заново откройте форму, чтобы получить актуальный CSRF-токен. Неудача запроса со старым токеном не доказывает исправление SQLi или XSS.

При каждом изменении уровня: **свежая форма → обычный ввод → тестовый ввод → исходник соответствующего уровня**. Это отделяет отказ защиты от недоступности приложения. Нельзя переносить ответ ЛР №6 в колонку «наблюдалось сейчас».

Время на готовом стенде: 5 минут подготовка, 15 SQLi, 15 Stored XSS, 10 команды, 10 файлы, 5 выводы. Если этап не выполнен, пометьте его явно; красивый отчёт не заменяет наблюдение.

## 1. SQLi: сравните Low, Medium и Impossible

| Уровень | Нормальная проба | Проверяемая проба | Что сравнить |
|---|---|---|---|
| Low | ID `1` | `' OR '1'='1` | Число разных записей |
| Medium | Выбор ID `1` | Сначала тот же строковый ввод, затем `1 OR 1=1` | Метод запроса, SQL-контекст, результат |
| Impossible | ID `1` из свежей формы | `1 OR 1=1` с актуальным токеном | Нормальная функция работает, дополнительный набор строк не возвращается |

В Medium UI показывает список значений вместо свободного поля. Это **клиентское ограничение**, а не доказательство серверной валидации. В Burp HTTP history выберите нормальный POST этой формы, **Send to Repeater**, измените только параметр `id`. Используйте редактор параметров или корректное URL-кодирование (`1%20OR%201%3D1`), сохраните запрос/ответ. Не переносите GET Low вслепую: Medium читает POST.

Откройте View Source трёх уровней. Для закреплённой версии ожидается: строковая конкатенация Low, числовой контекст с escaping в Medium, параметризация и проверка входа в Impossible. **Ожидание не является результатом опыта.** Если Medium возвращает несколько пользователей для числовой пробы, это показывает, почему escaping кавычек не защищает числовой SQL-контекст. Если ответ другой, проверьте форму, метод, Cookie, уровень и код; сохраните расхождение.

Вывод ограничьте проверенным модулем и входами. Название Impossible не является сертификатом безопасности всего DVWA.

## 2. Stored XSS: источник и повторное выполнение

1. Установите Low. Откройте **XSS (Stored)**. Добавьте обычное сообщение `LAB07 baseline`, имя `L7`.
2. Добавьте второе сообщение: `<script>alert('LAB07-STORED')</script>`, имя `L7`.
3. Сохраните запрос на добавление и снимок выполнения JavaScript.
4. Перейдите на другую страницу, затем снова откройте **XSS (Stored)** обычным GET без повторной отправки POST. Повторное окно при чтении подтверждает сохранение опасного содержимого. Сохраните этот GET и ответ отдельно.
5. В Low-исходнике найдите запись сообщения в БД и сравните с обработкой сообщения в Impossible.

**Перед сравнением уровней сохраните доказательства и очистите только учебную БД:** откройте Setup / Reset DB, нажмите Create / Reset Database. Это удаляет учебные сообщения и восстанавливает исходные данные. Войдите снова. База этого проекта специально выделена; к другим БД эта операция не применяется.

Теперь установите Impossible, откройте свежую форму и добавьте нормальный комментарий, затем **новое** сообщение с той же нагрузкой. Перейдите на страницу повторно. Зафиксируйте, отображается ли текст без выполнения JavaScript, как он представлен в ответе и что изменилось в обработке данных.

Переключение уровня само по себе не очищает ранее записанный вредоносный контент. Поэтому сравнение старого сообщения Low с новым уровнем без очистки смешивает **предотвращение новой записи** и **обработку ранее загрязнённых данных**. Для реального исправления необходимо учитывать оба случая.

## 3. Командная инъекция: один заблокированный разделитель

В **Command Injection** проведите по две пробы на Low, Medium и Impossible:

```text
127.0.0.1
127.0.0.1; whoami
```

Сохраняйте нормальный результат и результат изменённого ввода для каждого уровня. Если `whoami` исчез, определите причину через View Source: удаление символов или проверка допустимого адреса. Не считайте удаление `;` доказательством защиты от всех shell-конструкций. В этой работе подбор других команд не требуется.

Опишите исправление: отказ от построения shell-строки из ввода, API без shell, строгая проверка ожидаемого типа и минимальные привилегии процесса. Отметьте, какие из этих мер действительно есть в исследованном коде, а какие вы только рекомендуете.

## 4. Path Traversal и включение файла

В **File Inclusion** повторите на Low, Medium и Impossible:

```text
?page=file1.php
?page=../../../../../../etc/passwd
?page=/etc/passwd
```

Записывайте три результата отдельно. Для закреплённой версии Medium удаляет подстроку `../`, но абсолютный путь проверяет иначе: успешное чтение по абсолютному пути показывает неполноту такой фильтрации. В Impossible найдите разрешённый список штатных файлов. Проверка считается содержательной только если `file1.php` остаётся доступным.

Не читайте секреты, хеши паролей и файлы хоста. Доказательство ограничено `/etc/passwd` учебного контейнера.

## 5. Связь с обнаружением и ответом на инцидент

Заполните четыре строки: **что видит HTTP-прокси → какое действие подтверждено приложением → какой дополнительный источник нужен защитнику**. Например, опасный SQL-параметр показывает попытку, несколько посторонних записей в ответе — наблюдаемое воздействие на конфиденциальность. Для подтверждения исполнения команды в рабочей среде полезен аудит процессов, а не только сетевой alert.

Эта работа не запускает IPS и не доказывает блокировку сети. При HTTPS пассивный сетевой сенсор без доступа к расшифровке может не видеть проверенные HTTP-параметры. Описывайте необходимость журналов приложения/прокси/конечной системы, а не обещайте обнаружение по недоступным данным.

## Что сдавать

- Матрицу повторных проверок с уровнем, нормальной пробой, изменённым вводом, фактическим эффектом и ссылкой на доказательство.
- Отдельную цепочку Stored XSS: запись → последующее чтение → исполнение; затем сравнение с чистой БД и защищённой обработкой.
- Для каждой уязвимости — место ошибки, предлагаемую защиту и границу вывода.
- Четыре строки о возможностях и ограничениях источников обнаружения.

В публичную копию не включайте Cookie, CSRF-токены, сырые сессии и личные данные. Отсутствие всплывающего окна или ошибка SQL сами по себе не равны устранению уязвимости.

После сохранения результатов на сервере:

```bash
sudo docker compose -f setup/compose.yaml down
```

Команда удалит контейнеры и сеть **только проекта `spvo-appsec`**, сохранив том БД. Не применяйте глобальный prune, не удаляйте другие контейнеры и не сбрасывайте firewall. Если нужен полный сброс учебной БД, `down -v` допустим только после сохранения всех результатов и осознанного решения удалить этот том. После остановки DVWA восстановите подключение NAT-кабеля обеих VM для дальнейших работ. Сервис `8080` остаётся для дальнейших работ.
