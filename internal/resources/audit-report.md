# Source/Accuracy Audit — v2.16

Дата: **09.09.2026**

## Итог

Аудит не выявил необходимости переписывать концепцию курса с нуля: базовые принципы IDPS, различие network/host visibility, методы detection, base-rate problem, passive/inline architecture и используемые Suricata keywords имеют authoritative support. Однако обнаружено несколько мест, где исходная формулировка была сильнее источника или смешивала официальный факт с нашей инженерной интерпретацией.

Критичные корректировки выполнены в v2.16.1-source-audit:

1. NDR/NTA больше не выдаются за строгую современную стандартизованную taxonomy; NIST NBA помечена как историческая классификация.
2. NGFW diagram больше не выглядит как универсальный фиксированный packet-processing order.
3. Target 2013 переписан с учётом природы Senate staff report и противоречивой/неполной публичной forensic picture.
4. Все голые `Best practice` в ключевых кейсах заменены либо прямыми рекомендациями authoritative source, либо `инженерным выводом курса`.
5. Base-rate/threshold section больше не утверждает, что любая правка «строже» автоматически повышает FN; trade-off привязан к decision threshold.
6. TLS 1.3 reference актуализирован до RFC 9846, который в июле 2026 заменил RFC 8446.
7. Detection Engineering workflow и positive/negative/variant regression matrix явно помечены как методика курса, вдохновлённая OISF suricata-verify, а не как обязательный официальный workflow OISF.
8. Thresholding уточнён: это механизм ограничения alert frequency, а не исправление detection logic; prevention actions требуют отдельной интерпретации.
9. ЛР №1 стала offline-first: PPA installation — optional path для чистой Ubuntu, а не обязательное действие каждого студента.
10. ЛР №1 и ЛР №2 получили честный QA status: source/docs verified, но конкретные runtime paths ещё требуют прогона на чистой Ubuntu 24.04 + Suricata 8.0.7.
11. Lab Pack 02 явно маркирован как synthetic corpus; ожидаемая Rule A/B/C matrix до runtime test не выдаётся за заранее подтверждённый engine output.

## Решение о дальнейшей разработке

Новые главы можно продолжать только по такой же схеме: до публикации главы формируется source map; real cases используют primary/near-primary material; слова `best practice` применяются только при наличии authoritative support; synthetic examples маркируются; executable labs имеют отдельный `docs verified` и `runtime verified` статус.

## Открытые пункты после source audit

Историческое состояние после v2.16.1: LabBox v0.1 и прежний Lab Pack 02 требовали отдельного runtime QA. Начиная с v2.23 основной сценарий — две VM, которые студент разворачивает по общей инструкции: Ubuntu Desktop `10.13.37.10` и Ubuntu Server `10.13.37.20`. Готовые образы преподавателя остаются резервным вариантом. Полный runtime QA на эталонном стенде, собранном по этой же инструкции, остаётся обязательным.

## v2.20 corrective note

Новая Глава 3 заменяет прежнюю линейную модель обработки на функциональную декомпозицию. Это закрывает известные ошибки, в которых detection ошибочно начинался только после stream reassembly/application parsing и где TCP-oriented processing выдавался за универсальную архитектуру IDPS.

Новая ЛР №2 больше не использует ранний Path Traversal/TP-FP-FN сценарий. Её задача соответствует Главе 2: доказать различие сетевого и хостового источников на собственных evidence. Linux Audit используется только как лёгкий источник host telemetry; работа не выдаёт его за самостоятельный HIDS-продукт.

Runtime-status ЛР №2: **RUNTIME QA REQUIRED** до полного прогона на эталонной Ubuntu VM с фактически используемой версией Suricata и Linux Audit.

## v2.21 corrective note — логика Главы 2 и воспроизводимость лабораторных

После повторного аудита признано, что прежний раздел «Что нужно запомнить» Главы 2 недостаточно следовал логике самой главы: он сводил материал к четырём лозунгам вместо прямой связи «тип IDPS → источник → доступные факты → границы вывода». Раздел заменён сводной матрицей и схемой выбора источника.

ЛР №1 и ЛР №2 получили обязательные предварительные проверки. Они не заменяют runtime QA: лабораторная считается проверенной для конкретного учебного образа только после ручного end-to-end прохождения всей студенческой инструкции на этом образе.

В ЛР №2 отказались от network namespace как основной учебной модели: клиент и сервер теперь действительно являются двумя VM. Один контролируемый HTTP-запрос создаёт сетевой след для Suricata и локальный файловый след для Linux Audit, что напрямую соответствует тезису Главы 2 «один эпизод → разные следы».

Linux Audit rule переведён с deprecated watch-синтаксиса `-w` на filesystem/syscall rule с `dir` + `perm`. Для live Suricata в virtual-veth стенде используется `-k none` как ограниченное учебное средство против checksum-offload артефактов; это отдельно маркировано как не-production настройка.

## v2.24 corrective note — Глава 4 и ЛР №3

Глава 4 полностью заменена и теперь соответствует замороженной дидактической структуре курса: «Где и как размещают IDS/IPS». Из неё намеренно убраны методы обнаружения — они переходят в будущую Главу 5.

Логические разграничения, зафиксированные в новой редакции:

- точка наблюдения ≠ логика обнаружения;
- точка наблюдения ≠ способ доставки копии (`SPAN`/`TAP`);
- passive/inline ≠ IDS/IPS как функция;
- сенсор на периметре ≠ доказанная внутренняя visibility;
- отсутствие записи у сенсора ≠ отсутствие события.

ЛР №3 изолирует одну переменную — **точку наблюдения**. Один и тот же HTTP marker и одно и то же правило SID 1000003 используются сначала на NAT-интерфейсе, затем на интерфейсе `IDPS-LAB`. Существование запроса подтверждается отдельным журналом приложения, поэтому отрицательный результат сенсора не используется как самостоятельное доказательство отсутствия трафика.

Статус ЛР №3: **RUNTIME QA REQUIRED** до полного прогона на эталонных Ubuntu Desktop/Server 24.04.x с фактически установленной версией Suricata.

## v2.27 corrective note — Глава 5 и ЛР №4

Глава 5 полностью заменяет прежний материал в `course/05-firewall-vs-idps.md`; legacy filename сохранён только ради стабильности существующих ссылок. Новый предмет главы — **принцип принятия detection decision после того, как источник, представление и точка наблюдения уже определены**.

Зафиксированы четыре основания решения в учебном эксперименте: сигнатурное условие, состояние/семантика, фиксированный порог над серией событий и аномальное сравнение с базовой моделью. Критический старый дефект `Behavioral = Anomaly` устранён: ЛР №4 применяет к одному набору `/catalog` событий два разных режима — фиксированный временной порог без базовой модели и сравнение всплеска с измеренным базовым профилем.

ЛР №4 спроектирована после отдельной consistency table и не вводит самостоятельное написание Suricata rules раньше Главы 6. State-machine `START → DATA → END`, marker `LAB4-KNOWN-BAD` и experiment field `phase` явно маркированы как synthetic teaching constructs. Ни сигнатурное совпадение, ни нарушение модели состояния, ни выполнение фиксированного порога, ни аномальное отклонение не объявляются доказательством компрометации.

Статус ЛР №4: shell/Python/JavaScript syntax и component logic **STATICALLY VERIFIED**; полный end-to-end сценарий на Ubuntu Desktop/Server 24.04.x — **RUNTIME QA REQUIRED**.
## v2.29-rc1 corrective note — Глава 6: правила и их семантика

Новая Глава 6 заменяет старую `legacy/course/06-detection-quality.md` в активной учебной последовательности. Старый материал про base-rate/качество обнаружения не удалён из архива, но больше не считается содержанием Главы 6.

Проверенные разграничения новой главы:

- метод обнаружения ≠ язык/синтаксис правила;
- header/область применения ≠ совпадение содержательного условия;
- sticky buffer/представление данных ≠ источник данных;
- `flow`/state context ≠ самостоятельная методология;
- `msg`/`sid`/`rev`/классификация ≠ detection condition;
- правило ≠ alert ≠ incident;
- thresholding/suppression ≠ исправление слишком широкой логики;
- `drop` в тексте правила ≠ гарантированное блокирование вне подходящего IPS/inline-режима.

Сквозной пример не создаёт новый учебный сценарий: используется уже знакомое правило ЛР №1 `SID 1000001`, а `ATTACK-LAB` остаётся явно синтетическим маркером. Технические утверждения проверены по официальной документации Suricata 8.x. ЛР №5 в этот релиз не входит.
